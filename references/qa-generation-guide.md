# 交互式问答生成指南

审查报告生成后，进入**交互式问答阶段**。本指南说明如何将审查中发现的问题转化为产品经理可回答的选择题，引导 PM 深入思考需求细节。

---

## 强制：使用 AskUserQuestion 选择框

在 **Claude Code** 中，阶段 2 **必须**调用内置工具 **`AskUserQuestion`** 弹出可点选 UI（与 Plan 模式同类选择框）。

| 规则 | 说明 |
|------|------|
| 必须调用工具 | 写「使用 AskUserQuestion」，不要只写「向用户提问」 |
| 禁止纯文字 A/B/C | 禁止用 Markdown 列表让 PM 打字回复代替选择框 |
| 等答案再继续 | 未收到点选结果前，不得进入阶段 3 / 写代码 |
| 推荐项第一 | `options[0]` 为技术推荐，label 可带 ✅，description 写取舍 |
| 单次题量 | 每次 `AskUserQuestion` 建议 1–4 题 |
| 降级 | 仅当环境无该工具时，才用文末 Markdown 格式，并告知 PM |

**AskUserQuestion 字段建议：**

- `question`：场景化问题（可含 1 句技术说明 + 简短 PRD 引用）
- `options[].label`：短选项名
- `options[].description`：该选项意味着什么（成本/体验/风险）
- `multi_select`：仅多选补充类问题为 true

---

## 整体流程

```
审查报告（17 维度问题清单）
        ↓
   问题转化引擎
        ↓
按维度分组生成选择题
        ↓
  AskUserQuestion 弹出选择框
        ↓
   PM 逐组点选
        ↓
  收集所有回答
        ↓
  进入 PRD 重生成阶段
```

## 问题转化原则

### 1. 每个审查问题 → 一道选择题

审查报告中发现的每个"阻断"和"重要"问题，都必须转化为一道选择题。"建议"级问题可酌情合并或跳过。

**转化公式：**

```
[审查问题] → [场景化提问] + [2-4 个选项] + [技术说明]
```

- **场景化提问**：不要问"你的数据模型是什么"——要问"优惠券系统需要记录哪些核心信息？以下是技术团队建议的几个方案，你倾向哪个？"
- **选项即决策**：每个选项代表一个不同的产品设计决策，不是对错之分，而是取舍之分。
- **技术说明**：在每个问题前用 1-2 句话说明"为什么技术团队需要这个信息"，让 PM 理解背后的工程考量。

### 2. 选项设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **互斥** | 选项之间不重叠，PM 只能选一个 | "仅限新用户" vs "仅限老用户" vs "不限" |
| **穷举** | 覆盖常见做法，加"其他"兜底 | A/B/C + 自定义输入 |
| **具体** | 选项不是抽象概念，是具体方案 | "券面值固定金额（如 ¥10）" 而非 "固定类型" |
| **含取舍说明** | 每个选项标注它意味着什么 | "（开发成本低，但灵活性差）" |
| **有推荐** | 技术团队推荐的选项排第一位并标注 | "✅ 推荐：…（技术评估最适合）" |

### 3. 问题分组策略

问题按**维度**分组。用 `AskUserQuestion` 时每轮 1–4 题；仅降级 Markdown 时单轮可到 8 题。分组顺序：

| 优先级 | 维度 | 原因 |
|--------|------|------|
| 第 1 轮 | D1 范围 + D2 功能完整性 | 先确认"做什么"再谈细节 |
| 第 2 轮 | D8 数据模型 + D9 业务规则 | 数据和规则是开发的骨架 |
| 第 3 轮 | D6 边界与异常 + D7 歧义 | 明确边界和消除歧义 |
| 第 4 轮 | D3 非功能性 + D4 可行性 + D10 风险 | 约束和风险最后确认 |
| 第 5 轮 | D11-D17 配套产物 | 原型/图表相关决策 |

每轮问完后，告知 PM 当前进度（如"第 2/5 轮，已回答 8 题，剩余约 15 题"）。

## 各维度问题模板

### D1 范围清晰度

**问题结构：**
```
[技术说明] PRD 中提到"XX"但未明确是否在本次范围内。开发需要确认边界。

Q: 「XX 功能」是否在本次开发范围内？
   A. ✅ 推荐：不在本次范围，延后至 V2（当前架构先预留接口）
   B. 在本次范围，作为独立模块开发
   C. 在本次范围，但简化为 XX 的子集
   D. 其他（请描述）
```

**示例：**
```
技术团队发现 PRD 提到"券分享"但未明确是否在本次范围。如果不确认，开发可能多做或漏做。

Q: 「券分享给好友」功能是否在本次开发范围内？
   A. ✅ 推荐：不在本次范围，延后至 V2（当前先预留分享按钮位置）
   B. 在本次范围，需要完整开发（分享到微信/朋友圈/复制链接）
   C. 在本次范围，但只做"复制链接"一种方式
   D. 其他（请描述）
```

### D2 功能完整性

**问题结构：**
```
[技术说明] 功能模块「XX」缺少以下必需章节：[列出缺失项]。开发需要这些信息才能开始。

Q: 关于「XX 功能」，请补充以下信息（可多选需要补充的项）：
   A. ✅ 推荐：补充全部缺失项（技术团队提供模板，PM 填写）
   B. 只补充「数据实体」和「业务规则」（其他用默认值）
   C. 只补充「异常处理」（其他参考类似功能）
   D. 其他（请描述）
```

### D8 数据模型

**问题结构：**
```
[技术说明] PRD 中提到了「XX」但未列出其数据属性。开发需要知道存哪些字段。

Q: 「XX 实体」需要记录哪些核心信息？
   A. ✅ 推荐：[技术团队建议的字段列表]（覆盖当前功能需求）
   B. [精简版字段列表]（只存必需字段，后续扩展）
   C. [完整版字段列表]（预留未来扩展字段）
   D. 其他（请列出需要的字段）
```

**示例：**
```
PRD 描述了优惠券功能，但未明确优惠券需要记录哪些数据。技术团队需要这些信息来设计数据库表。

Q: 「优惠券」需要记录哪些核心信息？
   A. ✅ 推荐：券ID、名称、面值、使用门槛、有效期类型、有效期值、状态、库存、领取时间、使用时间（覆盖当前功能需求）
   B. 精简版：券ID、名称、面值、有效期、状态、库存（只存必需字段）
   C. 完整版：推荐版 + 适用商品范围、适用用户群体、发放渠道、叠加规则（预留扩展）
   D. 其他（请列出需要的字段）
```

### D9 业务规则

**问题结构：**
```
[技术说明] PRD 中「XX 规则」缺少以下细节：[具体缺失]。这会导致开发实现不确定。

Q: 关于「XX 规则」，请选择最符合产品预期的方案：
   A. ✅ 推荐：[方案A描述]（[技术评估理由]）
   B. [方案B描述]（[意味着什么]）
   C. [方案C描述]（[意味着什么]）
   D. 其他（请描述）
```

**示例：**
```
PRD 写了"每人限领1张"但没说如果重复领取会怎样。开发需要知道系统的处理方式。

Q: 用户尝试重复领取同一张优惠券时，系统应该如何处理？
   A. ✅ 推荐：按钮直接置灰不可点，提示"您已领取过该券"（体验好，避免无效请求）
   B. 允许点击但后端返回错误，Toast 提示"您已领取过该券"（实现简单）
   C. 允许领取但覆盖之前的券（不推荐，会造成数据混乱）
   D. 其他（请描述）
```

### D6 边界与异常

**问题结构：**
```
[技术说明] PRD 未覆盖「XX 异常场景」。如果不定义，开发会自行实现（可能与预期不符）。

Q: 当发生「XX 异常」时，用户应该看到什么？
   A. ✅ 推荐：[推荐方案]（[理由]）
   B. [方案B]（[意味着什么]）
   C. [方案C]（[意味着什么]）
   D. 其他（请描述）
```

**示例：**
```
PRD 没有描述"用户选了券但下单时券刚好过期"的情况。这是一个真实会发生的边界场景。

Q: 用户选了优惠券，但在提交订单的那一刻券刚好过期了，系统应该怎么处理？
   A. ✅ 推荐：提示"该优惠券已过期"，自动取消选中，订单按原价计算（用户可继续下单）
   B. 阻止下单，强制提示"请重新选择优惠券"（更安全但体验差）
   C. 仍然使用该券，后端兜底处理（不推荐，可能产生资损）
   D. 其他（请描述）
```

### D7 歧义检测

**问题结构：**
```
[技术说明] PRD 中「XX」有多种解读方式，开发需要确认唯一含义。

Q: PRD 中提到的「XX」具体指什么？
   A. ✅ 推荐：[精确含义A]（[理由]）
   B. [精确含义B]
   C. [精确含义C]
   D. 其他（请描述）
```

**示例：**
```
PRD 写了"按时间排序"，但开发不知道是哪个时间字段、正序还是倒序。

Q: 优惠券列表的"按时间排序"具体指？
   A. ✅ 推荐：按领取时间倒序（最新的在最前面，符合用户预期）
   B. 按领取时间正序（最先领的在前面）
   C. 按券的有效期排序（快过期的在前面，促使用户尽快使用）
   D. 其他（请描述）
```

### D3 非功能性需求

**问题结构：**
```
[技术说明] PRD 中「XX」非功能性需求没有量化指标，开发无法验收。

Q: 「XX 需求」的量化指标应设定为？
   A. ✅ 推荐：[推荐指标]（[基于行业标准的理由]）
   B. [更高标准]（[意味着更高的开发成本]）
   C. [更低标准]（[可能影响用户体验]）
   D. 其他（请描述）
```

### D4 技术可行性

**问题结构：**
```
[技术说明] PRD 中存在约束冲突/依赖风险：[具体描述]。需要 PM 做出取舍。

Q: 关于「XX 约束/依赖」，如何处理？
   A. ✅ 推荐：[推荐方案]（[理由]）
   B. [方案B]（[意味着什么]）
   C. [方案C]（[意味着什么]）
   D. 其他（请描述）
```

### D10 风险识别

**问题结构：**
```
[技术说明] 技术团队识别到以下风险：[风险描述]。需要 PM 确认应对策略。

Q: 对于「XX 风险」，产品侧的预期是？
   A. ✅ 推荐：[推荐策略]（[理由]）
   B. [策略B]（[意味着什么]）
   C. [策略C]（[意味着什么]）
   D. 其他（请描述）
```

### D11-D17 配套产物

**问题结构：**
```
[技术说明] PRD 缺少「XX 图表/原型」。这是开发的必需输入。

Q: 「XX 产物」将如何提供？
   A. ✅ 推荐：PM 在问答结束后补充提供（技术团队提供模板）
   B. 由技术团队根据 PRD 描述推导生成，PM 事后确认
   C. 本次不做，开发自行理解（风险：可能返工）
   D. 其他（请描述）
```

### D16 时序图

**问题结构：**
```
[技术说明] PRD 缺少核心交互的时序图。开发需要知道前端、后端、外部系统之间的调用顺序和事务边界。

Q: 「XX 交互场景」（如领取/用券/退券）的时序图将如何提供？
   A. ✅ 推荐：技术团队根据 PRD 描述推导生成，PM 事后审核确认
   B. PM 在问答结束后补充提供
   C. 本次不画时序图，开发自行推导（风险：事务边界不清）
   D. 其他（请描述）
```

**示例：**
```
PRD 描述了领取/用券/退券流程，但没有时序图展示系统组件之间的调用顺序。缺少时序图会导致开发不知道谁先调谁、事务边界在哪里。

Q: 核心交互场景（领取优惠券、下单用券、订单取消退券）的时序图将如何提供？
   A. ✅ 推荐：技术团队根据本次确认的 PRD 内容推导生成，PM 事后审核确认（确保调用顺序符合业务规则）
   B. PM 在问答结束后补充提供
   C. 本次不画时序图，开发自行推导
   D. 其他（请描述）
```

### D17 ER 实体关系图

**问题结构：**
```
[技术说明] PRD 有数据实体表，但缺少 ER 图展示实体之间的关系（1:1、1:N、N:M）。开发靠这个设计数据库外键和索引。

Q: 数据实体之间的关系图（ER 图）将如何提供？
   A. ✅ 推荐：技术团队根据 PRD 数据实体表推导生成，PM 事后审核确认
   B. PM 在问答结束后补充提供
   C. 本次不画 ER 图，开发自行理解（风险：关系设计错误）
   D. 其他（请描述）
```

## 问题数量控制

| PRD 状态 | 预估问题数 | 分轮数 |
|----------|-----------|--------|
| 简化版 PRD（只有功能描述） | 30-50 题 | 5 轮 |
| 完整版 PRD（有部分图表） | 15-30 题 | 3-4 轮 |
| 完善 PRD（只有少量缺口） | 5-15 题 | 1-2 轮 |

**控制原则：**
- AskUserQuestion 单次不超过 4 题（避免表单过长）；Markdown 降级时单轮不超过 8 题
- 阻断级问题优先问完
- 同一维度的多个问题合并为一道多选题（如"以下 5 个异常场景，请逐一选择处理方式"）
- 如果某维度审查无问题，跳过该维度，不生成空问题

## 问答输出格式

### 主路径：AskUserQuestion（必须）

每轮调用 `AskUserQuestion`，例如一题：

- **question**: `「券分享给好友」是否在本次开发范围内？`  
  （可附：技术说明 + PRD 原文摘要）
- **options**:
  1. label `✅ 不在本次范围，延后 V2` — description `当前架构预留接口，避免范围蔓延`
  2. label `在本次范围，完整开发` — description `含微信/朋友圈/复制链接，工期更长`
  3. label `在本次范围，只做复制链接` — description `最小可用分享能力`
- 等待点选结果后再问下一题/下一轮

### 降级路径：Markdown（仅无 AskUserQuestion 时）

```markdown
## 第 X 轮 / 共 Y 轮 — 维度名称

> **技术说明：** [为什么需要问这组问题，1-2 句话]

### Q1. [问题标题]

[问题背景，引用 PRD 原文]

- A. ✅ 推荐：[选项A] —— [取舍说明]
- B. [选项B] —— [取舍说明]
- C. [选项C] —— [取舍说明]
- D. 其他（请描述）

### Q2. [问题标题]

...

---
请逐题作答。如果某个选项不完全符合你的想法，选"其他"并描述你的方案。
```

## 回答收集格式

PM 作答后，将回答整理为结构化数据，供 PRD 重生成阶段使用：

```markdown
## PM 回答记录

### D1 范围清晰度

| 问题编号 | 问题摘要 | PM 选择 | 选择说明 |
|---------|---------|--------|---------|
| Q1 | 券分享是否在范围内 | A | 延后至 V2，预留接口 |
| Q2 | ... | B | ... |

### D8 数据模型

| 问题编号 | 问题摘要 | PM 选择 | 选择说明 |
|---------|---------|--------|---------|
| Q5 | 优惠券实体字段 | A | 采用推荐字段列表 |
| Q6 | ... | C | ... |

...
```

这份回答记录将作为 PRD 重生成阶段的输入之一。
