# 交互式问答生成指南

审查报告生成后，进入**交互式问答阶段**。本指南说明如何将审查问题转化为选择题，引导 PM 决策。

---

## 强制：默认直接触发点选 UI（多端）

阶段 2 **默认路径 = 立刻 tool call 弹出点选 UI**。报告交付后不要停、不要问「要不要提问」，同一轮就调用工具。

### 工具探测顺序（有则立刻 call，先于长文）

1. `request_user_input` → **Codex**
2. `AskUserQuestion` 或 `ask_user_question` → **Claude Code / Grok**
3. 其它同构多选题工具（若运行时暴露）
4. **仅**不存在或调用失败 → 一句说明 + Markdown 降级

| 环境 | 工具名 | 单次题量 | 选项数 |
|------|--------|----------|--------|
| Codex | `request_user_input` | 1–3（prefer 1） | 2–3 |
| Claude Code | `AskUserQuestion` | 1–4 | 2–4 |
| Grok | `ask_user_question` | 1–4 | 2–4 |
| 降级 | Markdown | ≤8 | 2–4 |

| 规则 | 说明 |
|------|------|
| **默认直接 call** | 探测到工具就立刻调用，先于任何长文 |
| 禁止征求许可 | 禁止「是否进入问答」「需要我提问吗」 |
| 禁止先写 Markdown 选项 | 有工具时禁止 A/B/C 文字列表代替选择框 |
| 等答案再继续 | 未收到点选结果前不得进入阶段 3 |
| 推荐项第一 | Claude/Grok 可用 ✅；Codex label 后缀 ` (Recommended)` |
| 不要手写 Other | 点选 UI **禁止**在 options 里加「其他/Other」；客户端自动提供 |
| 选项数 | 点选：实质方案 **2–4** 个（Codex 2–3）；**不要**凑第四个「其他」 |
| 只读 Plan | 无法点选时提示用户进入可交互模式 / 开 feature，再 Markdown |
| 轻量模式 | SKILL 判定为「只审不改」时 **整段跳过**本指南 |

### 字段映射

| 概念 | Claude / Grok | Codex |
|------|---------------|-------|
| 题干 | `question` | `question` |
| 选项短名 | `options[].label` | `options[].label` |
| 取舍说明 | `options[].description` | `options[].description` |
| 推荐项 | 第一；可选 ✅ | 第一；` (Recommended)` |
| header / id | 可选 | `header` ≤12 字符；`id` snake_case |
| multi_select | 仅多选补充类 | 通常无；拆题或说明 |

### Codex — `request_user_input` 示例

```json
{
  "questions": [
    {
      "id": "d6_coupon_expired",
      "header": "异常-过期",
      "question": "用户选了券但提交订单时券刚好过期，系统应如何处理？",
      "options": [
        {
          "label": "取消选中并按原价 (Recommended)",
          "description": "提示已过期，用户可继续下单，体验与资损风险平衡"
        },
        {
          "label": "阻止下单强制重选",
          "description": "更安全但摩擦更大"
        },
        {
          "label": "仍使用该券后端兜底",
          "description": "可能产生资损，不推荐"
        }
      ]
    }
  ]
}
```

| 字段 | 规则 |
|------|------|
| `options` | **2–3** 个；**禁止**含 Other |
| `autoResolutionMs` | 可选 60000–240000；**阻断题不要设** |
| 非交互 | `codex exec` 等无此工具 → Markdown |

**Codex 可用性：** `request_user_input` 默认只在 **Plan 模式**注册；Default 需 `~/.codex/config.toml` 中 `[features] default_mode_request_user_input = true`，且**新开会话**生效。

### Claude / Grok

- `question`：场景化（可含 1 句技术说明 + 短 PRD 引用）
- `options[].label` / `description`：短名 + 取舍（成本/体验/风险）
- `multi_select`：仅多选补充类为 true
- Grok 工具名多为小写 `ask_user_question`，字段语义与 Claude 对齐

## 整体流程

```
审查报告（17 维度问题清单）
        ↓
   问题转化引擎
        ↓
按维度分组生成选择题
        ↓
  【默认立刻】AskUserQuestion / request_user_input 弹出选择框
  （不征求许可、不先输出 Markdown 选项）
        ↓
   PM 逐组点选
        ↓
  收集所有回答
        ↓
  进入 PRD 重生成阶段
```

## 问题转化原则

### 1. 阻断/重要 → 选择题；建议默认跳过

默认只转化**阻断**和**重要**。"建议"级写入报告跟进项，不进问卷（除非 PM 要求深挖）。

**转化公式：**

```
[审查问题] → [场景化提问] + [2-4 个选项] + [技术说明]
```

- **场景化提问**：不问抽象模型，问具体场景决策。
- **选项即决策**：取舍之分，不是对错。
- **技术说明**：1–2 句说明工程为何需要该决策。

### 1.1 单问题单主维度（去重，强制）

| 问题性质 | 主维度 |
|----------|--------|
| 范围 / 模块章节缺失 | D1 / D2 |
| 异常、空态、断网等 | D6 |
| 表述歧义 | D7 |
| 字段/实体清单 | D8 |
| 业务规则与后果 | D9 |
| 直接决定**验证图结构**的不确定点（状态转换、cardinality、时序分支、流程穷尽、用户路径断点） | D12–D17 |
| 有图且与 PRD 不一致 | 对应 D11–D17 |

- **禁止**同一事实开两道题（例如 D9「取消后退券」+ D14「状态回退」各一）→ 只保留一题，优先 D6/D9；若答案将直接画进状态机，题干可注明「将用于生成状态机」。
- D11 未提供原型时**不生成**「何时补原型」类题。

### 1.2 同型缺口合并（强制，控题量）

多个模块/场景缺**同一类**信息时，审查报告可列多条，阶段 2 **合并为一题**（或一组 multi_select 补充项）：

| 同型 | 合并问法示例 |
|------|----------------|
| 多模块都无异常表 | 「以下模块的异常策略统一采用？」+ 推荐默认（空态/断网/防重复） |
| 多列表都未写排序 | 「列表类默认排序？」一条覆盖，例外模块再单问 |
| 多实体缺次要字段 | 「非 P0 实体字段完整度？」精简/推荐/完整三选一 |
| 多处 NFR 未量化 | 一条「性能/可用性默认指标包」 |

**不要合并：** 资损/安全相关规则、范围 In/Out、状态回退与库存后果、P0 模块的核心业务规则。

P0 / In-Scope 核心路径优先占独立题位；P1/P2 同型优先合并。

### 2. 选项设计原则

| 原则 | 说明 |
|------|------|
| **互斥** | 选项不重叠 |
| **穷举常见做法** | 点选：2–4 个实质方案即可，**勿**手写 Other；Markdown 降级可写「其他」 |
| **具体** | 具体方案，非抽象概念 |
| **含取舍说明** | 成本 / 体验 / 风险 |
| **有推荐** | 技术推荐项排第一 |

### 3. 问题分组策略

| 优先级 | 维度 | 原因 |
|--------|------|------|
| 第 1 组 | D1 + D2 | 先确认做什么 |
| 第 2 组 | D8 + D9 | 数据与规则骨架 |
| 第 3 组 | D6 + D7 | 边界与歧义 |
| 第 4 组 | D3 + D4 + D10 | 约束与风险 |
| 第 5 组 | D11–D17 | 有图一致性 + 仅图结构相关的不确定点 |

每轮可附一行进度（如「第 2/5 组，已答 6/12」），**不能替代 tool call**。

## 各维度问题模板

> **点选 UI 模板只有 A/B/C（或至多 4 个实质选项）。禁止写「D. 其他」——客户端自动提供 Other。**  
> Claude/Grok 推荐项可用 ✅；Codex 推荐项用 label 后缀 ` (Recommended)`，不要混用两套记号。  
> 下方示例以 Claude/Grok 记号书写；调 Codex 时改写推荐 label。

### D1 范围清晰度

**问题结构：**
```
[技术说明] PRD 中提到"XX"但未明确是否在本次范围内。开发需要确认边界。

Q: 「XX 功能」是否在本次开发范围内？
   A. ✅ 推荐：不在本次范围，延后至 V2（当前架构先预留接口）
   B. 在本次范围，作为独立模块开发
   C. 在本次范围，但简化为 XX 的子集
```

**示例：**
```
技术团队发现 PRD 提到"券分享"但未明确是否在本次范围。如果不确认，开发可能多做或漏做。

Q: 「券分享给好友」功能是否在本次开发范围内？
   A. ✅ 推荐：不在本次范围，延后至 V2（当前先预留分享按钮位置）
   B. 在本次范围，需要完整开发（分享到微信/朋友圈/复制链接）
   C. 在本次范围，但只做"复制链接"一种方式
```

### D2 功能完整性

**问题结构：**
```
[技术说明] 功能模块「XX」缺少以下必需章节：[列出缺失项]。开发需要这些信息才能开始。

Q: 关于「XX 功能」缺失规格，本次如何补齐？
   A. ✅ 推荐：按技术模板补齐数据实体 + 业务规则 + 异常（阶段 3 写入 PRD）
   B. 只补数据实体和业务规则；异常用行业默认并标 ❓
   C. 多模块统一用同一套默认规格包（适合同型缺口）
```

### D8 数据模型

**问题结构：**
```
[技术说明] PRD 中提到了「XX」但未列出其数据属性。开发需要知道存哪些字段。

Q: 「XX 实体」需要记录哪些核心信息？
   A. ✅ 推荐：[技术团队建议的字段列表]（覆盖当前功能需求）
   B. [精简版字段列表]（只存必需字段，后续扩展）
   C. [完整版字段列表]（预留未来扩展字段）
```

**示例：**
```
PRD 描述了优惠券功能，但未明确优惠券需要记录哪些数据。技术团队需要这些信息来设计数据库表。

Q: 「优惠券」需要记录哪些核心信息？
   A. ✅ 推荐：券ID、名称、面值、使用门槛、有效期类型、有效期值、状态、库存、领取时间、使用时间（覆盖当前功能需求）
   B. 精简版：券ID、名称、面值、有效期、状态、库存（只存必需字段）
   C. 完整版：推荐版 + 适用商品范围、适用用户群体、发放渠道、叠加规则（预留扩展）
```

### D9 业务规则

**问题结构：**
```
[技术说明] PRD 中「XX 规则」缺少以下细节：[具体缺失]。这会导致开发实现不确定。

Q: 关于「XX 规则」，请选择最符合产品预期的方案：
   A. ✅ 推荐：[方案A描述]（[技术评估理由]）
   B. [方案B描述]（[意味着什么]）
   C. [方案C描述]（[意味着什么]）
```

**示例：**
```
PRD 写了"每人限领1张"但没说如果重复领取会怎样。开发需要知道系统的处理方式。

Q: 用户尝试重复领取同一张优惠券时，系统应该如何处理？
   A. ✅ 推荐：按钮直接置灰不可点，提示"您已领取过该券"（体验好，避免无效请求）
   B. 允许点击但后端返回错误，Toast 提示"您已领取过该券"（实现简单）
   C. 允许领取但覆盖之前的券（不推荐，会造成数据混乱）
```

### D6 边界与异常

**问题结构：**
```
[技术说明] PRD 未覆盖「XX 异常场景」。如果不定义，开发会自行实现（可能与预期不符）。

Q: 当发生「XX 异常」时，用户应该看到什么？
   A. ✅ 推荐：[推荐方案]（[理由]）
   B. [方案B]（[意味着什么]）
   C. [方案C]（[意味着什么]）
```

**示例：**
```
PRD 没有描述"用户选了券但下单时券刚好过期"的情况。这是一个真实会发生的边界场景。

Q: 用户选了优惠券，但在提交订单的那一刻券刚好过期了，系统应该怎么处理？
   A. ✅ 推荐：提示"该优惠券已过期"，自动取消选中，订单按原价计算（用户可继续下单）
   B. 阻止下单，强制提示"请重新选择优惠券"（更安全但体验差）
   C. 仍然使用该券，后端兜底处理（不推荐，可能产生资损）
```

### D7 歧义检测

**问题结构：**
```
[技术说明] PRD 中「XX」有多种解读方式，开发需要确认唯一含义。

Q: PRD 中提到的「XX」具体指什么？
   A. ✅ 推荐：[精确含义A]（[理由]）
   B. [精确含义B]
   C. [精确含义C]
```

**示例：**
```
PRD 写了"按时间排序"，但开发不知道是哪个时间字段、正序还是倒序。

Q: 优惠券列表的"按时间排序"具体指？
   A. ✅ 推荐：按领取时间倒序（最新的在最前面，符合用户预期）
   B. 按领取时间正序（最先领的在前面）
   C. 按券的有效期排序（快过期的在前面，促使用户尽快使用）
```

### D3 非功能性需求

**问题结构：**
```
[技术说明] PRD 中「XX」非功能性需求没有量化指标，开发无法验收。

Q: 「XX 需求」的量化指标应设定为？
   A. ✅ 推荐：[推荐指标]（[基于行业标准的理由]）
   B. [更高标准]（[意味着更高的开发成本]）
   C. [更低标准]（[可能影响用户体验]）
```

### D4 技术可行性

**问题结构：**
```
[技术说明] PRD 中存在约束冲突/依赖风险：[具体描述]。需要 PM 做出取舍。

Q: 关于「XX 约束/依赖」，如何处理？
   A. ✅ 推荐：[推荐方案]（[理由]）
   B. [方案B]（[意味着什么]）
   C. [方案C]（[意味着什么]）
```

### D10 风险识别

**问题结构：**
```
[技术说明] 技术团队识别到以下风险：[风险描述]。需要 PM 确认应对策略。

Q: 对于「XX 风险」，产品侧的预期是？
   A. ✅ 推荐：[推荐策略]（[理由]）
   B. [策略B]（[意味着什么]）
   C. [策略C]（[意味着什么]）
```

### D11-D17 产物一致性与推导不确定点

**问题来源有两类，同等处理：**

1. **PM 提供了原型/图时**：审查发现的一致性问题（如"PRD 写 Tab 在顶部，原型在左侧，以哪个为准"）。
2. **未提供图时**：阶段 1 从 PRD 文字推导隐含模型（状态流转、流程分支、调用时序、实体关系、用户路径）中无法唯一确定的点。

**不要问"什么时候补图"**——图由阶段 3 根据本阶段确认的答案自动生成。这里问的是图背后的**产品决策**：每个不确定点都是一道场景化选择题，问法与 D6/D9 相同（具体场景 + 互斥选项 + 取舍说明）。

**问题结构：**
```
[技术说明] PRD 未说明「XX 场景」的处理方式，推导存在多种合理解读。这个决策会影响「XX 验证图」的生成。

Q: 「XX 场景」下系统应该如何处理？
   A. ✅ 推荐：[方案A]（[理由]）
   B. [方案B]（[意味着什么]）
   C. [方案C]（[意味着什么]）
```

**示例（D14 状态流转）：**
```
PRD 写了"订单可取消"，但没有说明取消后已使用的券如何处理。这决定了状态机中是否存在"已使用→未使用"的回退转换。

Q: 用户取消订单后，该订单已使用的优惠券应该如何处理？
   A. ✅ 推荐：退回为"未使用"状态，有效期不变（符合用户预期，行业常见做法）
   B. 直接作废，标记为"已失效"（防止薅羊毛，但用户体验差）
   C. 退回但重新计算有效期（从退回之日起重新计时）
```

**示例（D17 实体关系）：**
```
PRD 同时提到"订单"和"优惠券"两个实体，但没有说明二者的数量关系。这决定了 ER 图中的 cardinality 和是否需要中间表。

Q: 一个订单允许使用几张优惠券？
   A. ✅ 推荐：每单限用 1 张，订单与券为 1:0..1 关系（实现简单，不易产生资损）
   B. 每单可用多张券，需要订单-券中间表（N:M）
   C. 每单可用多张，但同类型券限 1 张（N:M + 互斥规则）
```

**示例（D16 调用时序）：**
```
PRD 写了"选券后下单"，但没有说明券有效性在哪一端校验。这决定了时序图中校验失败分支的画法。

Q: 用户选券下单时，券有效性（过期/门槛/互斥）应在哪里校验？
   A. ✅ 推荐：前端选券时初筛 + 后端下单时最终校验，以后端为准（体验与资损风险平衡）
   B. 仅后端下单时校验（实现简单，但用户选了不能用的券要到提交才发现）
   C. 仅前端校验（不推荐，可被绕过产生资损）
```

**异域示例（B 端配置 / 内容审核，避免只会问电商）：**

```
# 配置发布
Q: 管理员修改了「功能开关」并点击发布，若此时有用户请求正在读取旧配置，系统应如何处理？
   A. ✅ 推荐：版本号原子切换，读请求绑定版本，发布中仍读旧版（避免半新半旧）
   B. 立即全局生效，不保证读一致性（实现简单，可能抖动）
   C. 发布时短暂拒绝所有读（强一致但可用性差）

# 内容审核
Q: 用户提交内容后审核驳回，用户是否可编辑后再次提交？
   A. ✅ 推荐：可编辑并重新进入待审，保留驳回原因（体验好、可审计）
   B. 不可再提，只能新建一条
   C. 自动再提一次给同一审核员（可能不公）
```

## 问题数量控制（硬闸门）

| 规则 | 值 |
|------|-----|
| 默认范围 | 仅阻断 + 重要 |
| 建议级 | 默认不进问卷 |
| **硬上限** | **≤ 15 题** |
| 深挖模式 | 用户明确要求时可 **≤ 25 题** |
| 超出上限 | 同维/**同型**合并；可行业默认的不占题位 → 阶段 3 填默认并标 ❓，同时写入报告「未澄清项」 |
| **禁止** | 静默丢弃重要/阻断问题；点选 options 手写 Other |

| 必须 PM 决策（优先占题位） | 可默认 + ❓（省题位） |
|------------------------------|----------------------|
| 范围边界、In/Out of Scope | 通用空态文案 |
| 资损/安全相关规则 | 常见 NFR 数字（需标注行业默认） |
| 互斥、状态回退、券/库存后果 | 非核心排序细节 |
| 验收歧义（过/不过不清晰） | 纯文案语气；**无独立验收章节**可阶段 3 代写模板标 🆕 |

| PRD 状态 | 目标题数（默认模式） |
|----------|----------------------|
| 简化版 | 尽量压到 ≤15（合并 + 默认） |
| 完整版 | 8–15 |
| 完善版 | 5–12 |

**其它原则：**
- 阻断优先；Claude/Grok 单次 **尽量打满** 1–4；Codex 1–3（极重题 prefer 1）；Markdown ≤8
- 同维/同型合并；无 multi_select 时拆题
- 某维无问题则跳过，不生成空题
- 首轮前用一行预告：「约 N 题 / 约 M 轮」

## 问答输出格式

### 主路径 A：Claude `AskUserQuestion` / Grok `ask_user_question`（必须）

每轮调用对应工具，例如一题：

- **question**: `「券分享给好友」是否在本次开发范围内？`  
  （可附：技术说明 + PRD 原文摘要）
- **options**:
  1. label `✅ 不在本次范围，延后 V2` — description `当前架构预留接口，避免范围蔓延`
  2. label `在本次范围，完整开发` — description `含微信/朋友圈/复制链接，工期更长`
  3. label `在本次范围，只做复制链接` — description `最小可用分享能力`
- 等待点选结果后再问下一题/下一轮

### 主路径 B：Codex `request_user_input`（必须）

```json
{
```
