# 状态机图审阅标准

维度 D14 审查时使用的基准。审查 PRD 中是否包含状态机图（State Machine Diagram），以及状态机图是否正确、完整、与业务规则一致。

本标准分 4 大块：A. 状态机完整性、B. 状态定义正确性、C. 转换完整性、D. 状态机与 PRD 一致性。

---

## A. 状态机完整性

### 查什么

PRD 是否为有状态的业务实体提供了状态机图？状态机图是否覆盖了该实体的完整生命周期？

### 合格

- PRD 为每个有状态的实体（订单、优惠券、任务、审批单等）提供了状态机图
- 状态机图有明确的初始状态（实心圆）
- 状态机图有终止状态（如果有终结状态的话——实心圆+外圈）
- 图中包含该实体的所有状态，没有遗漏 PRD 业务规则中提到的状态
- 每个状态有名称，状态名是名词或形容词（如"未使用"、"已过期"），不是动作

### 缺失（标记为阻断/重要）

- PRD 中的实体有"status"字段但没有状态机图 → 重要
- 状态机图缺少初始状态 → 重要
- PRD 业务规则提到了"已冻结"状态但状态机图中没有 → 阻断
- 状态名是动词（如"用户支付"而不是"已支付"） → 建议
- 一个实体的状态机图超过 8 个状态且无嵌套/子状态 → 建议（可读性问题）

---

## B. 状态定义正确性

### 查什么

状态定义是否合理？是否存在状态爆炸、状态冗余、或状态与属性混淆？

### 合格

- 状态是该实体生命周期的不同阶段，不是属性值的组合
- 状态数量可控（一个图不超过 7-8 个状态，复杂情况用嵌套状态）
- 没有冗余状态（两个状态功能相同可以合并）
- 没有将状态与活动（Activity）混淆（状态是条件，活动是正在执行的动作）

### 缺失（标记为重要）

| 反模式 | 状态机中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 状态爆炸 | 优惠券有 12 个独立状态 | 状态过多难以维护，应考虑嵌套或属性化 | 建议 |
| 状态属性混淆 | 为"VIP用户已使用"和"普通用户已使用"各设一个状态 | 用户类型是属性不是状态，应保留"已使用"状态，用户类型作为属性 | 重要 |
| 冗余状态 | "待发货"和"已打包待发货"作为两个独立状态 | 如果行为完全相同，应合并 | 建议 |
| 状态名是动作 | 状态叫"用户点击领取" | 状态应该是"已领取"（条件），不是动作 | 建议 |
| 缺少嵌套 | 订单有"待支付/已支付/已发货/已签收/已退款/已取消"6+ 状态 | 可以用嵌套状态（"进行中"包含已支付/已发货/已签收） | 建议 |

---

## C. 转换完整性

### 查什么

每个状态转换是否都有触发事件和守卫条件？是否存在不可达状态、死锁、或守卫条件不完整？

### 合格

- 每个状态转换都有明确的触发事件（如"用户操作"、"超时"、"系统定时任务"）
- 如果有多个转换从同一状态出发且触发事件相同，有互斥且完整的守卫条件（Guard）
- 每个状态至少有一个出转换（除非它是终止状态）
- 守卫条件覆盖了所有可能的情况（没有"遗漏分支"）
- 转换上有明确的动作（Action）说明转换时系统做什么（如"发送通知"、"记录日志"）

### 缺失（标记为阻断/重要）

| 反模式 | 状态机中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 不可达状态 | "已冻结"状态没有任何入转换 | 这个状态永远无法进入，代码写了也执行不到 | 重要 |
| 死锁状态 | "处理中"状态没有超时转换，也没有错误处理转换 | 一旦进入就无法离开，系统卡死 | 阻断 |
| 守卫条件不完整 | 从"未使用"出发有两个事件相同的转换："[券在有效期内]→已使用"和"[券已过期]→已过期"，但缺了"[券不存在]"分支 | 遗漏分支导致未定义行为 | 重要 |
| 守卫条件不互斥 | 从同一状态出发的两个转换守卫条件可以同时为真 | 状态机行为不确定 | 重要 |
| 无触发事件 | 转换线上只有箭头没有事件名 | 不知道什么触发这个转换 | 重要 |
| 缺少回退转换 | "已使用"的券取消订单后没有回到"未使用"的转换 | PRD 业务规则允许取消，但状态机没体现 | 阻断 |
| 无超时处理 | "待支付"状态没有超时自动取消的转换 | 订单永远停留在待支付，数据堆积 | 重要 |
| 缺少动作 | 转换线上没有标注系统做什么 | 开发不知道状态变化时要触发什么业务逻辑 | 建议 |

---

## D. 状态机与 PRD 一致性

### 查什么

状态机图中的状态、转换、事件是否与 PRD 的功能模块、业务规则、数据实体表一致？

### 合格

- 状态机中的每个状态都能在 PRD 数据实体表的"status"字段枚举值中找到
- 状态机中的每个转换触发事件都能在 PRD 操作规则表中找到对应的用户操作
- 状态机中的守卫条件与 PRD 业务规则一致（如 PRD 规则"有效期 30 天"对应守卫条件"[领取时间 ≤ 30 天]"）
- 状态机的初始状态与 PRD 数据实体表的默认值一致
- 状态转换时的系统动作（Action）在 PRD 功能模块中有对应的描述

### 缺失（标记为阻断/重要）

| 反模式 | PRD 写的 | 状态机画的 | 严重程度 |
|--------|---------|-----------|---------|
| 状态不一致 | PRD 数据实体 status 有 5 个枚举值 | 状态机只有 3 个状态 | 阻断 |
| 转换与规则冲突 | PRD 规则"过期券不可用" | 状态机有过期券→已使用的转换 | 阻断 |
| 事件缺失 | PRD 操作规则表有"用户取消订单"操作 | 状态机中没有"取消"事件 | 重要 |
| 守卫与规则不符 | PRD 规则"满 100 元才能用券" | 状态机守卫条件是"[订单金额 > 100]"（缺了等于） | 重要 |
| 动作未描述 | 状态机转换动作"发送过期提醒短信" | PRD 功能模块中没有这个功能的描述 | 建议 |
| 初始状态不一致 | PRD 写"新券默认状态为未使用" | 状态机初始状态是"已发放" | 重要 |
| 缺少终止状态 | PRD 写"订单完成后进入归档" | 状态机没有终止/归档状态 | 建议 |

---

## 审查结论判定

状态机审查完成后，结合以下规则给 D14 维度打分：

| 分数 | 含义 | 标准 |
|------|------|------|
| **3** | 优秀 | 状态机完整、状态定义合理、转换无遗漏、守卫互斥且完整、与 PRD 完全一致。 |
| **2** | 合格 | 仅有建议级问题。基本完整，少量状态命名或守卫条件不够精确。 |
| **1** | 需改进 | 发现有重要问题。缺少部分转换、守卫不完整、或与 PRD 有不一致。 |
| **0** | 严重缺失 | 有阻断级问题。完全没有状态机、或有死锁/不可达状态/与规则冲突等严重错误。 |
