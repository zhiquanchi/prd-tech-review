# ER 实体关系图审查标准

维度 D17 审查时使用的基准，双重用途：PM 提供了 ER 实体关系图（Entity-Relationship Diagram）→ 阶段 1 按本标准审查；未提供 → 不定级，阶段 3 生成 ER 图（数据实体 ≥ 2 且有关联时）后按本标准自检。ER 图直观展示数据实体之间的关联关系（1:1、1:N、N:M），是数据库表设计的基础。PRD 中的数据实体表（11 项标准第 7 项）列出了属性和规则，但 ER 图展示的是**关系**——哪个实体依赖哪个、删除时是否级联、查询时需要 JOIN 哪些表。开发靠这个设计数据库索引和外键约束。

---

## 1. ER 图完整性

### 查什么

PRD 中定义的所有数据实体是否在 ER 图中出现？实体之间的关系是否完整？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| PRD 数据实体表中的所有实体都在 ER 图中 | 优惠券、用户券、用户、操作日志都在 | 有实体未画出 → 阻断 |
| 每个实体都有主键标注 | 实体框中标注主键字段（PK） | 无主键 → 重要 |
| 实体之间的关系都有 cardinality 标注 | 1:1、1:N、N:M 明确标注 | 无 cardinality → 重要 |
| 关系有方向性说明 | 从属关系明确（如"用户拥有用户券"） | 关系方向不明 → 建议 |
| 外键关系在 ER 图中体现 | 用连线或标注显示外键引用 | 无外键标注 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 实体遗漏 | PRD 有 4 个实体，ER 图只画了 3 个 | 遗漏的实体关系未定义 | 阻断 |
| 关系缺失 | 用户和用户券之间没有画关系线 | 开发不知道是一对多还是多对多 | 阻断 |
| 无 cardinality | 画了线但没标 1:N 或 N:M | 开发不知道建表时是否需要中间表 | 重要 |
| 循环依赖 | A 依赖 B，B 依赖 C，C 依赖 A | 数据库设计无法落地 | 阻断 |
| 关系与 PRD 规则冲突 | PRD 写"一个用户可持有多张券"，ER 图画成 1:1 | 直接矛盾 | 阻断 |

## 2. ER 图规范正确性

### 查什么

ER 图是否符合数据库设计规范？是否存在会导致性能问题或数据不一致的设计？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 无冗余实体 | 每个实体都有独立存在的意义 | 可通过计算/派生得到的实体也画了 → 建议 |
| 无属性重复 | 同一属性只在一个实体中定义 | 多个实体有重复属性 → 重要 |
| N:M 关系有中间表 | 多对多关系通过中间实体/关联表实现 | 直接连 N:M 没有中间表 → 阻断 |
| 弱实体有依赖标注 | 如"用户券"依赖"用户"和"优惠券"存在 | 弱实体未标注依赖 → 建议 |
| 有索引设计建议 | 高频查询字段建议建索引 | 无索引建议 → 建议 |
| 无过度规范化 | 不超过 3NF，必要时适当反规范化 | 过度拆分导致 JOIN 过多 → 建议 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| N:M 无中间表 | 用户和优惠券画成 N:M 但没有关联实体 | 关系型数据库无法直接实现 N:M | 阻断 |
| 属性冗余 | 用户实体和订单实体都有"手机号" | 更新不同步导致数据不一致 | 重要 |
| 派生实体独立画 | "优惠后金额"作为独立实体 | 可通过计算得到，不需要独立存储 | 建议 |
| 缺少弱实体标识 | 用户券没有标注依赖哪个强实体 | 开发不知道删除用户时是否级联删除用户券 | 重要 |
| 主键设计不当 | 用业务字段（如手机号）做主键 | 业务字段可能变更，主键不应变更 | 重要 |

## 3. ER 图与 PRD 一致性

### 查什么

ER 图中的实体、属性、关系是否与 PRD 数据实体表、业务规则一致？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| ER 图中的实体与 PRD 数据实体表一一对应 | 实体名称、属性一致 | 不一致 → 阻断 |
| ER 图中的关系与 PRD 业务规则一致 | PRD 写"一个用户可持有多张券"，ER 图是 1:N | 不一致 → 阻断 |
| ER 图中的外键与 DFD 数据存储一致 | DFD 中的数据存储在 ER 图中有对应实体 | 不一致 → 重要 |
| ER 图中的属性类型与 API 契约一致 | 实体中"面值"是 decimal，API 也返回 decimal | 不一致 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 实体名不一致 | PRD 叫"优惠券"，ER 图叫"Coupon"且无映射 | 开发对不上 | 重要 |
| 属性不一致 | PRD 有"使用门槛"，ER 图没有 | 遗漏字段 | 阻断 |
| 关系与规则矛盾 | PRD 写"每人限领 1 张"，ER 图画成 N:M | 直接矛盾 | 阻断 |
| 与 DFD 不一致 | DFD 有"订单库"但 ER 图没有"订单"实体 | 数据模型不完整 | 重要 |

## 4. ER 图画法要求

| 要求 | 说明 |
|------|------|
| 使用标准 ER 图符号 | 矩形=实体，椭圆=属性，菱形=关系，连线=关联 |
| 主键标注 PK | 在属性名旁标注 (PK) |
| 外键标注 FK | 在属性名旁标注 (FK) 并指向引用实体 |
| cardinality 标注在连线两端 | 如 `1` — `N`、 `0..1` — `*` |
| 多对多必须有中间实体 | 不要直接在两个实体间画 N:M |
| 标注必要索引 | 在实体旁用注释标注建议索引字段 |
| 弱实体用双线矩形 | 依赖其他实体存在的实体用双线边框 |
