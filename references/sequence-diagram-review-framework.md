# 时序图审查标准

PRD 是否为核心交互流程提供了时序图（Sequence Diagram）？时序图展示系统组件（前端、后端、外部系统）之间的调用顺序、消息传递和时序依赖。开发靠这个理解接口交互顺序、事务边界和异常回滚点。详细审查标准如下。

---

## 1. 时序图完整性

### 查什么

时序图是否覆盖了所有需要跨系统/跨层调用的核心场景？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 每个涉及外部系统调用的功能都有时序图 | 领券、用券、退券、退款都有时序图 | 只有部分场景有时序图 → 重要 |
| 时序图有明确的参与者定义 | 每个泳道/参与者都有角色名称（用户、App 前端、优惠券服务、订单服务、用户中心） | 参与者未定义 → 重要 |
| 时序图标注了同步/异步调用 | 每个箭头标注 sync/async | 未标注 → 建议 |
| 时序图标注了接口名称 | 每个调用箭头标注具体接口名（如 `POST /api/coupon/claim`） | 未标注接口名 → 重要 |
| 核心异常路径有时序图 | 超时、失败、回滚的时序路径 | 只有正常流程 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 无时序图 | PRD 完全没有时序图 | 开发不知道谁先调谁，联调时扯皮 | 重要 |
| 参与者不完整 | 只画了前端和优惠券服务，没画订单服务 | 遗漏订单服务调用，接口遗漏 | 阻断 |
| 无异常路径 | 只画了正常领取流程 | 超时后怎么处理？回滚逻辑在哪里？ | 重要 |
| 无事务边界 | 领券扣库存和写用户券记录之间没有标注事务 | 库存扣了但用户券没写成功 → 数据不一致 | 阻断 |
| 循环/条件未标注 | 重试逻辑没画出来 | 开发不知道是否需要重试、重试几次 | 重要 |
| 接口名缺失 | 箭头只写"调用接口" | 开发不知道调什么端点 | 重要 |

---

## 2. 时序正确性

### 查什么

调用顺序是否符合业务逻辑？是否存在时序上的矛盾？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 校验在前，操作在后 | 先校验用户是否已领取，再扣库存 | 先扣库存再校验 → 阻断 |
| 状态更新顺序正确 | 先锁定券，再调用支付，支付成功后再标记已使用 | 先标记已使用再调用支付 → 阻断 |
| 回退路径完整 | 订单取消时，先回退券状态，再通知订单系统 | 只有成功路径，无回退 → 重要 |
| 并发控制点在时序图中标注 | 扣库存前加锁、释放锁的时序 | 未标注并发控制 → 重要 |
| 外部回调的时序正确 | 支付回调后才标记订单完成，回调超时后走主动查询 | 未处理回调超时 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 先写数据再校验 | 先写用户券记录再校验是否已领取 | 可能重复写入脏数据 | 阻断 |
| 状态更新过早 | 券在支付前就标记"已使用" | 支付失败后券已消耗 → 资损 | 阻断 |
| 无回退时序 | 订单取消时只通知了订单系统，没通知券系统 | 券永远被锁定 | 阻断 |
| 回调缺失超时处理 | 等待支付回调，没画超时主动查询的分支 | 回调丢失时订单永远挂起 | 阻断 |
| 锁释放遗漏 | 加了分布式锁但没画释放锁的时序 | 死锁 | 阻断 |

## 3. 时序图与 PRD 一致性

### 查什么

时序图中的调用顺序是否与 PRD 的操作规则表、业务规则一致？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 时序图中的每个步骤对应 PRD 操作规则表中的操作 | PRD 写了"校验库存→扣库存→写用户券"，时序图一一对应 | 时序图步骤与 PRD 不一致 → 阻断 |
| 时序图中的接口对应 API 契约 | 时序图调 `POST /api/coupon/claim`，API 文档有该端点 | 时序图接口在 API 文档中找不到 → 重要 |
| 时序图中的状态转换与状态机图一致 | 状态机图有"锁定→已使用"，时序图有对应的触发事件 | 不一致 → 阻断 |
| 时序图中的数据流与 DFD 一致 | DFD 中的数据流在时序图中有对应的接口调用 | 不一致 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 时序与操作规则冲突 | PRD 写"先校验再扣减"，时序图"先扣减再校验" | 直接矛盾 | 阻断 |
| 状态转换缺失 | 状态机图有 5 个状态，时序图只涉及 3 个 | 遗漏状态转换场景 | 重要 |
| 接口名不一致 | 时序图调 `claimCoupon`，API 文档叫 `receiveCoupon` | 开发不知道按哪个命名 | 重要 |

## 4. 推荐的时序图场景

以下场景**强烈建议**提供时序图：

| 场景 | 为什么必须有时序图 |
|------|-------------------|
| 领取优惠券 | 涉及库存扣减 + 用户券写入，需要事务边界 |
| 下单用券 | 涉及券锁定 + 订单创建 + 支付回调，需要回退路径 |
| 订单取消/退款退券 | 涉及状态回退，需要确认回退时序 |
| 支付回调处理 | 涉及异步回调 + 超时处理 + 主动查询 |
| 高并发场景 | 涉及分布式锁 + 幂等校验 + 重试 |

---

## 5. 时序图画法要求

| 要求 | 说明 |
|------|------|
| 使用标准 UML 时序图语法 | 参与者、生命线、消息箭头、激活条、alt/opt/loop 片段 |
| 每个参与者一条生命线 | 不要合并多个角色到一条线 |
| 标注接口名和 HTTP 方法 | `POST /api/coupon/claim` 而非"调用领券接口" |
| 标注同步/异步 | sync 用实线箭头，async 用开放箭头 |
| 标注事务边界 | 用矩形框或注释标注事务开始/提交/回滚 |
| 包含异常分支 | 用 alt 片段标注正常路径和异常路径 |
| 包含超时处理 | 标注超时时间和超时后的处理分支 |
