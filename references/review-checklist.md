## D1 范围清晰度

### 查什么
PRD 必须在"做"和"不做"之间画一条硬线。开发者靠这个估算工作量、避免做了又被砍掉的功能。

### 审查问题
- 有没有明确的"Out of Scope"章节？没有 → 阻断。
- 每个 Out-of-Scope 项是否说明了*为什么*排除，而不只是*排除什么*？
- 有没有"Future"项需要现在就预留接口/数据？有但没标注 → 重要。
- 范围边界是否可判定——开发者能否指着某个功能明确说"在范围内"或"不在范围内"？

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 兜底词 | "优惠券等功能" | "等"让范围开放式结束，开发不知道还包括什么 | 重要 |
| "参考现有功能" | "支付流程参考现有逻辑" | 哪个现有逻辑？当前支付流程在多端有 3 个版本 | 重要 |
| 无边界"其他" | "以及其他常见支付方式" | 开发无法穷举"其他"——可能是 2 种也可能是 20 种 | 重要 |
| Out-of-Scope 无原因 | "券分享：不做" | 没给原因，开发无法判断是永久排除还是延后 | 建议 |
| 范围蔓延信号 | "如果时间允许，可以加上 XX" | "如果时间允许"不是需求——是愿望。要么在范围内，要么不在 | 重要 |

## D2 功能完整性

### 查什么
每个功能模块必须有 11 项框架中的必需章节。缺少必需章节意味着开发只能靠猜，导致返工。

### 审查问题
- 每个功能模块是否有：功能说明、页面布局、操作流程、操作规则表、数据展示？
- 每个模块是否有数据实体？没有 → 阻断。
- 每个模块是否有带后果说明的业务规则？没有 → 阻断。
- 每个模块是否有异常处理？没有 → 阻断。
- 范围里提到了模块但没有详细展开？→ 阻断。
- 详细展开了但范围里没提到？→ 重要（范围/详情不一致）。

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 模块被引用但没展开 | 范围写了"下单选券"但没有对应模块章节 | 开发没有可实施的规格 | 阻断 |
| 缺数据实体 | 模块描述了券列表 UI 但没有数据实体表 | 开发不知道券有哪些字段 | 阻断 |
| 缺业务规则 | 功能写了"用户可以使用优惠券"但没有规则表 | 开发不知道：能叠加吗？有门槛吗？过期规则？ | 阻断 |
| 缺异常处理 | 只描述了正常流程 | 开发会猜错误状态——而且会猜错 | 阻断 |
| 操作规则不完整 | 布局里提到了按钮但操作规则表里没有 | 开发不知道点击后发生什么 | 重要 |

## D3 非功能性需求可量化性

### 查什么
每个非功能性需求必须用可衡量的数字表达。定性词不可测，会导致主观的验收争议。

### 审查问题
- 每个非功能性需求：有没有具体的数字或阈值？
- 衡量方式是否定义了（怎么验证这个数字）？
- 并发量是否匹配预期用户规模、是否现实？
- 有没有整个缺失的非功能性需求（如支付功能没有安全要求）？

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 应该写成 | 严重程度 |
|--------|-------------|---------|---------|
| 定性性能 | "页面加载要快" | "首屏 ≤ 2s（4G 网络），接口响应 ≤ 500ms（P95）" | 重要 |
| 定性稳定性 | "系统要稳定" | "可用性 ≥ 99.9%，单点故障恢复 ≤ 5min" | 重要 |
| 模糊并发 | "支持高并发" | "支持峰值 QPS 5000，日常 QPS 500" | 重要 |
| 无衡量方式 | "响应 ≤ 200ms"（但怎么测？） | "接口 P95 响应 ≤ 200ms（服务端日志统计）" | 建议 |
| 缺安全需求 | 支付功能没有安全要求 | 补充："支付信息传输使用 TLS 1.2+，卡号不落库" | 重要 |

## D4 技术可行性

### 查什么
约束之间必须自洽且可实现。依赖必须有备选方案。排期必须匹配范围。

### 审查问题
- 约束之间是否冲突？（如"必须原生实现" + "2 周内双端上线"）
- 排期对于范围是否可行？如果范围大排期紧，有没有分期方案？
- 对其他团队/系统的依赖是否列出了预期交付日期？
- 每个依赖：如果没按时交付有没有备选方案？
- 有没有不合理地限制解决方案空间的技术约束？

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 约束冲突 | "原生实现" + "3 天上线" + "双端" | 3 天原生双端不现实 | 阻断 |
| 依赖无日期 | "依赖支付团队提供接口" | 没有预期交付日期——无法规划联调 | 重要 |
| 依赖无备选 | 依赖 B 团队 API，没有 B 方案 | B 团队延期则整个功能阻断 | 重要 |
| 排期不现实 | 2 个开发 2 周 10 个模块 | 范围与产能不匹配 | 阻断 |
| 约束无影响说明 | "必须兼容 IE8" | 没说明代价（限制 UI 框架选择） | 重要 |

## D5 验收可测性

### 查什么
每条验收标准测试后必须能产生明确的通过/不通过结果。主观标准会导致验收扯皮。

### 审查问题
- 每条验收标准能否测试并产生明确的通过或失败？
- 有没有验收标准？PRD 没有验收测试章节 → 阻断。
- 验收用例是否覆盖了边界场景，而不只是正常流程？
- 预期结果是否足够具体可判定？（如"展示 3 张未使用券，按领取时间倒序"而不是"显示正常"）
- 有没有全局验收清单（兼容性、性能、数据准确性、埋点）？

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 应该写成 | 严重程度 |
|--------|-------------|---------|---------|
| 主观标准 | "体验流畅" | "页面滚动 FPS ≥ 55，点击响应 ≤ 200ms" | 重要 |
| 模糊预期结果 | "显示正常" | "展示 3 张未使用券，按领取时间倒序，每张显示面值、名称、有效期" | 重要 |
| 无验收章节 | PRD 没有验收测试章节 | 必须补充验收用例 | 阻断 |
| 只有正常流程 | 5 条用例全是正常场景 | 补充：空态、断网、过期数据、并发操作 | 重要 |
| 缺全局检查 | 没有兼容性/性能/埋点清单 | 补充全局验收清单 | 重要 |

## D6 边界与异常覆盖

### 查什么
PRD 必须说明出问题时怎么办。开发最怕没提到的场景——只能猜，而且会猜错。

### 审查问题
对每个功能模块，检查以下场景是否覆盖：
- **空态** — 没有数据时用户看到什么？
- **断网** — 接口调用失败时怎么办？
- **加载中** — 等待时用户看到什么？
- **数据过多** — 数据量太大怎么办？（分页？虚拟滚动？）
- **无权限** — 用户未登录或没有权限怎么办？
- **并发操作** — 用户快速点两次"提交"怎么办？
- **过期/无效数据** — 券在页面加载后、使用前刚过期怎么办？
- **非法输入** — 用户输入特殊字符、超长文本、类 SQL 内容怎么办？

每个缺失场景 = 重要。

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 缺了什么 | 严重程度 |
|--------|-------------|---------|---------|
| 无空态 | 列表页没有空态说明 | 0 张券时用户看到什么？ | 重要 |
| 无断网处理 | 没提离线/错误状态 | 开发会用系统默认错误页——体验差 | 重要 |
| 无防重复点击 | 提交按钮没有防抖说明 | 用户可重复提交，产生重复订单 | 重要 |
| 无加载说明 | 没提骨架屏/转圈 | 开发自选加载 UX | 建议 |
| 未处理过期数据 | 券列表没处理加载到使用之间的过期问题 | 用户选了已过期券——下单失败报错不明 | 重要 |

## D7 歧义检测

### 查什么
每句需求描述必须只有一种解读。如果两个开发读出来不一样，就是歧义。

### 审查问题
- 排序是否指定了字段名+方向？（"按领取时间倒序"而不是"按时间排序"）
- 列表是否穷举，没有"等"？（"支持微信、支付宝"而不是"支持微信等"）
- 是否使用了未定义的"相关" / "相应" / "适当"？
- 数量是否具体？（"展示 10 条"而不是"展示多条"）
- 条件分支是否完整？（如果 X 则 A；那如果不是 X 呢？）

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 为什么歧义 | 让 PM 明确什么 | 严重程度 |
|--------|-------------|-----------|--------------|---------|
| 排序未指定 | "按时间排序" | 哪个时间字段？正序还是倒序？ | "明确：按 created_at 倒序" | 重要 |
| 开放式列表 | "支持常见支付方式" | 哪些？ | "穷举：微信支付、支付宝、银联" | 重要 |
| 未定义"相关" | "展示相关信息" | 什么信息？ | "明确字段：券名称、面值、有效期、状态" | 重要 |
| 条件不完整 | "如果用户是会员，显示专享价" | 不是会员呢？ | "补充：非会员显示原价，无专享标识" | 重要 |
| 数量模糊 | "展示多条数据" | 多少条？ | "明确：每页 10 条，滑到底自动加载下 10 条" | 重要 |

## D8 数据模型健全性

### 查什么
所有数据实体及其属性必须显式列出。功能描述中隐含但没列入实体表的实体 = 缺口。

### 审查问题
- 功能描述中的所有名词是否都对应数据实体？
- 每个实体是否列出了 UI 引用的所有属性？
- 实体之间的关系是否清晰？（如"一个用户有多张券"——有没有写明？）
- 有没有业务规则里用到但实体表里没列的属性？
- 有没有计算/派生字段？如果有，计算规则是否说明了？

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 缺了什么 | 严重程度 |
|--------|-------------|---------|---------|
| 隐含实体未列出 | 功能提到"订单"但实体表里没有订单 | 补充订单实体及属性 | 重要 |
| UI 字段不在实体中 | UI 显示"券剩余数量"但实体没有"remaining_count"属性 | 给实体补充属性 | 重要 |
| 关系不清晰 | 用户和券都列了但没说明关系 | 补充："用户 1:N 券（一个用户可持有多张券）" | 重要 |
| 派生字段无规则 | UI 显示"优惠后价格"但没有计算公式 | 补充："实付金额 = 订单金额 - 券面值，最小为 0" | 重要 |
| 缺状态字段 | 实体没有"status"属性但 UI 显示状态标识 | 补充状态字段及枚举值 | 重要 |

## D9 业务规则完备性

### 查什么
每条业务规则必须有"违反了会怎样"的后果。逐个用户操作走查，问"如果……怎么办"来发现未覆盖场景。

### 审查问题
- 每条业务规则是否有编号、类型、描述、后果？
- 有没有未覆盖的"如果……怎么办"场景？走查：
  - 如果用户重复做 X 怎么办？
  - 如果条件 Y 不满足怎么办？
  - 如果数据 Z 刚变了（过期、删除、被其他流程修改）怎么办？
- 时效类规则是否明确了时区？（"有效期 30 天"——从什么时候算？哪个时区？）
- 计算规则是否精确？（不能有浮点歧义——"优惠 = 面值"而不是"优惠按比例"）
- 互斥规则是否说明了？（同一订单不能同时用两张券）

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 缺了什么 | 严重程度 |
|--------|-------------|---------|---------|
| 规则无后果 | "每人限领 1 张"但没写"重复领取怎么办" | 补充："重复领取时提示'您已领取过该券'，按钮置灰" | 重要 |
| 时效规则无锚点 | "有效期 30 天" | 从什么时候算 30 天？（领取时？发放时？） | 重要 |
| 计算无精度 | "优惠按比例计算" | 什么精度？四舍五入还是向下取整？（如"优惠 = 订单金额 × 折扣率，保留 2 位小数，向下取整"） | 重要 |
| 缺互斥规则 | 没有关于券叠加的规则 | 补充："同一订单只能使用 1 张券，不可叠加" | 重要 |
| 未覆盖"如果" | 券功能但没处理"选券和支付之间券过期了" | 补充明确规则和处理方式 | 重要 |

## D10 风险识别

### 查什么
识别这份 PRD 中最可能导致返工、范围蔓延或集成失败的地方。这是"开发最担心什么"的维度。

### 审查问题
- 有没有未声明的假设？（PM 假设 X 成立但没写下来）
- 有没有看起来简单但有隐藏复杂度的功能？（如"加个搜索"——但搜索需要索引、排序、分页、空结果、慢查询处理……）
- 有没有跟其他系统的集成点还没讨论过？
- PRD 中有没有依赖尚未搭建的基础设施？
- 有没有数据迁移问题？（新功能需要现有数据做转换）
- 有没有范围蔓延风险？（功能描述模糊到"再加一个"不断发生）

### 需要标记的反模式

| 反模式 | PRD 中的例子 | 隐藏风险 | 严重程度 |
|--------|-------------|---------|---------|
| 未声明假设 | 假设"用户已登录"但没写进假设章节 | 未登录则整个流程崩溃，无登录跳转说明 | 重要 |
| 看着简单的复杂功能 | "加个搜索" | 需要：搜索引擎、索引策略、排序、分页、空态、防抖——不是 1 天的活 | 重要 |
| 集成未讨论 | 功能需要从 3 个现有系统取数据，无集成方案 | 集成测试、数据一致性、API 契约全部未定义 | 重要 |
| 基础设施依赖 | "实时推送"但没有 WebSocket 基础设施 | 需要新建基础设施——影响排期 | 重要 |
| 数据迁移 | 给现有券加新状态字段，无迁移方案 | 现有券没有状态——默认值是什么？ | 重要 |

## D11 UI 原型与 PRD 一致性

### 查什么

产品使用 Ant Design 框架编写的 UI 原型是审查的必需输入。PRD 描述"做什么"，原型展示"怎么交互"——两者必须一致。同时审查 Ant Design 组件是否被正确使用。详细标准见 `ui-prototype-framework.md`。

### 审查问题

**原型完整性：**
- PRD 中提到的每个页面，原型里是否都有对应的 Ant Design 组件实现？没有 → 阻断。
- 原型是可交互的 React 代码，还是静态截图/ Figma 导出？静态 → 阻断。
- 原型能否走通主流程？（点击按钮、切换 Tab、提交表单）走不通 → 重要。

**Ant Design 组件使用规范：**
- 有没有手写 Ant Design 已有组件能实现的功能？（手写表格/弹窗/下拉/Tab/分页）→ 重要。
- 组件 API 是否正确？（`dataSource` 不是 `data`、`open` 不是 `visible`、`onFinish` 不是 `onSubmit`）→ 重要。
- `<Form.Item>` 的 `name` 是否与数据字段对应？不对应 → 重要。
- 布局是否用了 `<Row>`/`<Col>`/`<Layout>`？没用 → 建议。
- 图标是否从 `@ant-design/icons` 引入？没用 → 建议。

**状态与交互覆盖：**
- 空态是否用了 `<Empty>` 组件？没有 → 重要。
- 加载态是否用了 `<Spin>`/`<Skeleton>`/Table `loading`？没有 → 重要。
- 表单字段是否有 `rules` 校验？没有 → 重要。
- 操作反馈是否用了 `message`/`notification`/`Modal.confirm`？用 `alert` → 建议；无反馈 → 重要。
- 列表是否配置了分页？没有 → 重要。

**PRD 与原型一致性：**
- PRD 布局章节描述的区域，原型是否都有？缺失 → 阻断。
- PRD 操作规则表的按钮行为，原型 `onClick` 是否一致？不一致 → 阻断。
- PRD 数据展示表的排序/数量/格式，原型是否一致？不一致 → 重要。
- PRD 异常处理表的场景，原型是否都实现了？未实现 → 重要。

### 需要标记的反模式

| 反模式 | 原型中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 原型缺失页面 | PRD 写了 5 个页面，原型只有 3 个 | 开发不知道缺失页面长什么样 | 阻断 |
| 静态原型 | 原型是 Figma 截图不是 Ant Design 代码 | 无法验证交互行为，开发要重新实现 | 阻断 |
| 手写表格 | `<div>` + `map` 拼 Table | 重复造轮子，丢失排序/分页/筛选能力 | 重要 |
| 手写弹窗 | `<div>` + `display:none` | 丢失 Modal 的遮罩/ESC 关闭/焦点管理 | 重要 |
| API 错误 | `<Table data={list}>` | `data` 不是合法 prop，表格不渲染数据 | 重要 |
| name 不匹配 | `<Form.Item name="userName">` 但字段是 `username` | 表单校验和取值都会失败 | 重要 |
| 缺空态 | `dataSource={[]}` 时页面空白 | 用户看到空白不知道什么情况 | 重要 |
| 缺加载态 | 请求时无 loading 反馈 | 用户以为页面卡死 | 重要 |
| 缺表单校验 | `<Form.Item>` 没有 `rules` | 提交非法数据到后端 | 重要 |
| 缺操作反馈 | 提交成功后页面无变化 | 用户不知道是否成功，会重复提交 | 重要 |
| 缺分页 | 列表无分页配置 | 数据量大时全量渲染，性能崩溃 | 重要 |
| PRD/原型不一致 | PRD 写"Tab 在顶部"原型在左侧 | 开发按哪个做？ | 重要 |
| 事件未绑定 | PRD 写"点击跳转"但 `onClick` 为空 | 原型不可走通，无法验证流程 | 阻断 |
| 用 alert 反馈 | `alert("提交成功")` | 偏离 Ant Design 规范，体验不一致 | 建议 |

## D12 UX 审阅

### 查什么

PRD 是否提供了 UX 用户流程图/用户旅程图？用户完成核心任务的路径是否高效？交互模式是否一致？错误体验是否完善？详细标准见 `ux-review-framework.md`。

### 审查问题

**UX 流程图完整性：**
- PRD 是否包含用户流程图/用户旅程图/信息架构图？没有 → 重要（阶段 2 追问补齐方式）。
- 流程图是否覆盖了正常流程 + 异常分支？只画正常流程 → 重要。
- 核心用户场景是否有对应的流程图？没有 → 重要。
- 信息架构是否展示了页面层级和导航关系？没有 → 重要。

**用户路径效率：**
- 核心任务完成需要多少步？超过合理步数 → 重要。
- 高频操作是否触手可及（不超过 2 次点击）？ buried 在深层导航 → 重要。
- 是否有返回/撤销路径？没有 → 重要。
- 是否有重复输入？有 → 建议。

**交互一致性：**
- 同类操作是否使用相同的交互模式？不一致 → 重要。
- 按钮语义（主操作/次要操作/危险操作）是否一致？不一致 → 重要。
- 错误提示呈现方式是否统一？不统一 → 建议。

**无障碍与错误体验：**
- 错误文案是否说明原因 + 给出操作建议？模糊文案 → 重要。
- 空态是否有引导性文案 + 操作入口？只有"暂无数据" → 重要。
- 危险操作是否有二次确认？没有 → 重要。
- 加载状态是否有明确反馈？没有 → 重要。

### 需要标记的反模式

| 反模式 | UX 中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无流程图 | PRD 完全没有 UX 流程图 | 开发不知道用户怎么走流程 | 重要 |
| 路径过长 | 领券需要 7 步 | 用户流失，转化率低 | 重要 |
| 深层导航 | 常用功能埋在 3 层菜单下 | 用户找不到 | 重要 |
| 无返回路径 | 进入页面后无法返回 | 用户困在死胡同 | 重要 |
| 同操作不同交互 | A 页面删除用弹窗，B 页面直接删 | 用户预期混乱 | 重要 |
| 错误文案模糊 | 只写"系统异常" | 用户不知道怎么办 | 重要 |
| 空态无引导 | "暂无数据"没有操作按钮 | 用户不知道接下来做什么 | 重要 |
| 危险操作无确认 | 删除直接执行 | 误删无法恢复 | 重要 |
| 无加载反馈 | 点击后页面无变化 | 用户重复点击 | 重要 |
| 按钮语义混乱 | 主操作按钮颜色不统一 | 用户不知道哪个是主操作 | 重要 |

## D13 DFD 数据流图审阅

### 查什么

PRD 是否提供了 DFD 数据流图？DFD 是否符合规范？分层是否平衡？DFD 与 PRD 是否一致？详细标准见 `dfd-review-framework.md`。

### 审查问题

**DFD 完整性：**
- PRD 是否包含 DFD 图（至少 Context 图或 Level 0）？没有 → 重要（阶段 2 追问补齐方式）。
- DFD 中是否出现了 PRD 提到的所有外部实体？缺失 → 重要。
- DFD 中是否出现了 PRD 数据实体表中的所有数据存储？缺失 → 重要。
- 加工是否有编号和功能描述？没有 → 重要。

**DFD 规范正确性：**
- 每个加工是否有输入和输出？只有输入（黑洞）或只有输出（白洞）→ 阻断。
- 输入数据是否足以产生输出（灰洞）？不足 → 重要。
- 外部实体是否直接读写数据存储？直连 → 阻断。
- 两个数据存储之间是否直接流动？直连 → 阻断。
- 两个外部实体之间是否直接流动？直连 → 阻断。
- 数据流是否被当成了控制流（标注"点击"、"触发"）？是 → 重要。

**分层一致性：**
- 父子图之间的数据流是否平衡？不平衡 → 重要。
- 数据存储在父子图中命名是否一致？不一致 → 建议。

**DFD 与 PRD 一致性：**
- DFD 中的每个加工是否对应 PRD 的功能模块？不对应 → 阻断。
- DFD 中的每个数据存储是否对应 PRD 的数据实体？不对应 → 阻断。
- DFD 数据流的粒度是否与 PRD 业务规则匹配？不匹配 → 重要。

### 需要标记的反模式

| 反模式 | DFD 中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无 DFD | PRD 完全没有数据流图 | 开发不知道数据怎么流 | 重要 |
| 黑洞 | 加工只有输入没有输出 | 数据消失，逻辑错误 | 阻断 |
| 白洞 | 加工只有输出没有输入 | 数据凭空产生，逻辑错误 | 阻断 |
| 灰洞 | 输入"用户ID"输出"完整订单" | 输入不足以产生输出 | 重要 |
| 实体直连存储 | 用户直接读写数据库 | 违反 DFD 规范 | 阻断 |
| 存储间直连 | 数据库 A 直接流向 B | 违反 DFD 规范 | 阻断 |
| 控制流当数据流 | 数据流叫"点击提交按钮" | DFD 不显示控制流 | 重要 |
| 父子图不平衡 | 父图有流子图没有 | 数据流丢失 | 重要 |
| 加工无对应模块 | DFD 有"核销"加工但 PRD 没这个功能 | DFD 和 PRD 不一致 | 阻断 |
| 存储无对应实体 | DFD 有"订单库"但 PRD 没这个实体 | DFD 和 PRD 不一致 | 阻断 |

## D14 状态机图审阅

### 查什么

PRD 是否为有状态实体提供了状态机图？状态定义是否合理？转换是否完整？状态机与 PRD 业务规则是否一致？详细标准见 `state-machine-review-framework.md`。

### 审查问题

**状态机完整性：**
- 有"status"字段的实体是否有状态机图？没有 → 重要。
- 状态机图是否有初始状态？没有 → 重要。
- 状态机是否覆盖了 PRD 业务规则中提到的所有状态？遗漏 → 阻断。

**状态定义正确性：**
- 状态是否是生命周期阶段而非属性组合？状态属性混淆 → 重要。
- 状态数量是否合理（≤8 个/图）？过多且无嵌套 → 建议。
- 状态名是否是名词/形容词而非动词？是动词 → 建议。

**转换完整性：**
- 每个状态是否有至少一个出转换（终止状态除外）？没有 → 阻断（死锁）。
- 每个转换是否有触发事件？没有 → 重要。
- 同一事件的多个转换守卫条件是否互斥且完整？不互斥/不完整 → 重要。
- 是否有不可达状态？有 → 重要。
- 是否缺少回退转换（如取消订单后券回到未使用）？缺少 → 阻断。
- 是否缺少超时处理（如待支付超时自动取消）？缺少 → 重要。

**状态机与 PRD 一致性：**
- 状态机中的状态是否与 PRD 数据实体 status 枚举一致？不一致 → 阻断。
- 转换是否与 PRD 业务规则冲突？冲突 → 阻断。
- 转换事件是否与 PRD 操作规则表对应？不对应 → 重要。
- 守卫条件是否与 PRD 业务规则一致？不一致 → 重要。

### 需要标记的反模式

| 反模式 | 状态机中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无状态机 | 实体有 status 字段但没有状态机图 | 开发不知道状态怎么流转 | 重要 |
| 死锁状态 | "处理中"没有出转换 | 一旦进入就卡住 | 阻断 |
| 不可达状态 | "已冻结"没有入转换 | 永远进不去，代码白写 | 重要 |
| 状态属性混淆 | "VIP用户已使用"作为独立状态 | 用户类型是属性不是状态 | 重要 |
| 守卫不完整 | 两个分支缺了第三种情况 | 未定义行为 | 重要 |
| 守卫不互斥 | 两个守卫可以同时为真 | 状态机行为不确定 | 重要 |
| 缺少回退 | 取消订单后券没回到未使用 | 与业务规则冲突 | 阻断 |
| 无超时处理 | "待支付"无超时转换 | 订单永远挂起 | 重要 |
| 状态不一致 | PRD 有 5 个枚举值状态机只有 3 个 | 遗漏状态 | 阻断 |
| 转换与规则冲突 | PRD 说过期不可用但状态机有过期→已使用 | 直接矛盾 | 阻断 |

## D15 业务流程图审阅

### 查什么

PRD 是否为每个核心业务流程提供了流程图（Flowchart）？处理逻辑是否正确？决策分支是否穷举？流程图与 PRD 及其他图表是否一致？详细标准见 `flowchart-review-framework.md`。

### 审查问题

**流程图完整性：**
- PRD 的核心业务流程是否有对应的流程图？没有 → 重要（阶段 2 追问补齐方式）。
- 每个流程图是否有明确的开始和结束节点？没有 → 重要。
- 流程图是否覆盖了异常分支（不只画"快乐路径"）？只画正常流程 → 重要。
- 步骤命名是否是动作短语（如"校验券有效期"）？是名词 → 建议。

**逻辑正确性：**
- 是否存在死循环（无限循环没有退出条件）？有 → 阻断。
- 是否存在不可达路径（某分支永远走不到）？有 → 重要。
- 是否存在逻辑矛盾（如"校验通过"后又判断"校验失败"）？有 → 重要。
- 并行处理步骤是否有汇合点？没有 → 重要。
- 上下游步骤的输入输出是否匹配？不匹配 → 重要。
- 每个可能失败的步骤是否有异常出口？没有 → 重要。

**决策分支完备性：**
- 每个决策点是否穷举了所有可能结果？遗漏 → 重要。
- 二元决策是否确实只有两种可能（有没有第三种被遗漏）？有 → 重要。
- 每个分支是否都导向明确的下一步？悬空分支 → 阻断。
- 多元决策是否有默认/兜底分支？没有 → 重要。
- 分支条件是否有可能重叠（如 >100 和 ≥100）？重叠 → 重要。
- 决策条件是否具体可判定（不是"是否满足条件"）？模糊 → 重要。
- 是否缺少超时分支（如"等待支付回调"只有成功/失败没有超时）？缺少 → 重要。
- 是否缺少并发/重复操作分支？缺少 → 重要。

**流程图与 PRD 一致性：**
- 流程图中的处理步骤是否对应 PRD 功能模块或业务规则？不对应 → 阻断。
- 决策条件是否与 PRD 业务规则一致？不一致 → 重要。
- 异常分支是否与 PRD 异常处理表对应？不对应 → 重要。
- 流程图入口/出口是否与 PRD 描述一致？不一致 → 重要。
- 状态变化是否与状态机图（D14）一致？不一致 → 重要。
- 数据操作是否与 DFD（D13）一致？不一致 → 重要。

### 需要标记的反模式

| 反模式 | 流程图中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无流程图 | 核心业务流程只有文字描述没有流程图 | 开发不知道处理逻辑怎么走 | 重要 |
| 死循环 | "重试"循环回自身没有最大次数 | 系统无限重试，资源耗尽 | 阻断 |
| 悬空分支 | "校验失败→"箭头指向空白 | 失败后不知道怎么办 | 阻断 |
| 不可达路径 | 分支前有永真守卫条件 | 分支永远走不到 | 重要 |
| 逻辑矛盾 | "校验通过"后又判断"校验失败" | 已通过不可能再失败 | 重要 |
| 分支遗漏 | "支付方式"只画微信/支付宝缺银联 | 没有穷举所有方式 | 重要 |
| 无默认分支 | 多元决策没有"其他"分支 | 未知类型无处理 | 重要 |
| 分支重叠 | ">100→A"和"≥100→B" | 100 元时走 A 还是 B？ | 重要 |
| 决策条件模糊 | 判断框写"是否满足条件" | 开发不知道判断什么 | 重要 |
| 缺超时分支 | "等待回调"只有成功/失败 | 一直不回调怎么办？ | 重要 |
| 缺并发分支 | 没有处理"同时提交两次" | 重复提交产生重复订单 | 重要 |
| 步骤无对应 | 流程图有"核销"步骤但 PRD 没这个功能 | 流程图和 PRD 不一致 | 阻断 |
| 条件不一致 | PRD"满100"流程图">100" | 缺了等于 | 重要 |
| 异常分支不匹配 | PRD 异常表有"断网重试"流程图没有 | 遗漏异常处理 | 重要 |
| 与状态机不一致 | 状态机有"已冻结"但流程图没有冻结步骤 | 图表之间矛盾 | 重要 |

## D16 时序图审阅

### 查什么

PRD 是否为核心交互流程提供了时序图（Sequence Diagram）？时序图展示用户、前端、后端之间的调用顺序、消息传递和请求-响应过程。开发靠这个理解用户操作触发的接口交互顺序和异常处理逻辑。详细标准见 `sequence-diagram-review-framework.md`。

### 审查问题

**时序图完整性：**
- PRD 是否包含核心交互的时序图？没有 → 重要。
- 时序图是否覆盖了所有涉及前后端交互的核心场景？遗漏 → 重要。
- 时序图是否有明确的参与者定义（用户、前端、后端）？没有 → 重要。
- 时序图是否标注了接口名称（具体端点和 HTTP 方法）？没有 → 重要。
- 核心异常路径（校验失败、网络错误、服务端异常）是否有时序分支？只有正常流程 → 重要。

**时序正确性：**
- 交互链路是否完整：用户操作 → 前端校验 → 请求 → 后端处理 → 返回 → 前端展示 → 用户感知？缺环节 → 重要。
- 是否先校验后提交、先请求成功再更新展示？前端先改展示再发请求 → 阻断。
- 失败时前端是否回退到操作前状态并提示用户？没有 → 重要。
- 并发控制（防抖/节流、请求竞态处理）是否标注？没有 → 重要。
- loading 状态的开始/结束时机是否标注？没有 → 建议。

**时序图与 PRD 一致性：**
- 时序图中的步骤是否与 PRD 操作规则表一一对应？不一致 → 阻断。
- 时序图中的接口名是否与 API 契约一致？不一致 → 重要。
- 时序图中的状态转换是否与状态机图（D14）一致？不一致 → 阻断。
- 时序图中的数据流是否与 DFD（D13）一致？不一致 → 重要。

### 需要标记的反模式

| 反模式 | 时序图中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无时序图 | PRD 完全没有时序图 | 开发不知道用户操作后谁先调谁，联调时扯皮 | 重要 |
| 参与者不完整 | 只画了前端和后端，没画用户操作起点 | 不知道操作触发来源和用户反馈路径 | 阻断 |
| 无异常路径 | 只画了正常提交成功流程 | 校验失败怎么提示？网络错误怎么处理？ | 重要 |
| 无请求-响应对应 | 只画前端发请求，没画后端返回和用户反馈 | 不知道返回什么数据、怎么展示给用户 | 重要 |
| 先改前端展示再发请求 | 用户点击后前端先改数据再调接口 | 接口失败后前端展示错误数据 → 数据不一致 | 阻断 |
| 无失败回退时序 | 提交失败时前端没画回退逻辑和错误提示 | 用户以为成功了，实际没保存 | 重要 |
| 请求竞态 | 快速切换 Tab，先后两个请求后发的先返回 | 页面展示旧数据 | 重要 |
| 无防抖/节流 | 用户快速点击按钮发了 N 个请求 | 后端压力大，可能重复提交数据 | 重要 |
| 接口名缺失 | 箭头只写"调用接口" | 开发不知道调什么端点 | 重要 |
| 时序与规则冲突 | PRD 写"先校验再提交"，时序图"先提交再校验" | 直接矛盾 | 阻断 |

## D17 ER 实体关系图审阅

### 查什么

PRD 是否提供了 ER 实体关系图（Entity-Relationship Diagram）？ER 图直观展示数据实体之间的关联关系（1:1、1:N、N:M），是数据库表设计的基础。开发靠这个设计外键约束和索引。详细标准见 `er-diagram-review-framework.md`。

### 审查问题

**ER 图完整性：**
- PRD 数据实体表中的所有实体是否在 ER 图中出现？有遗漏 → 阻断。
- 每个实体是否有主键标注？没有 → 重要。
- 实体之间的关系是否有 cardinality 标注（1:1、1:N、N:M）？没有 → 重要。
- 外键关系是否在 ER 图中体现？没有 → 重要。

**ER 图规范正确性：**
- 是否有冗余实体（可通过计算/派生得到的独立实体）？有 → 建议。
- 是否有属性重复（同一属性在多个实体中定义）？有 → 重要。
- N:M 关系是否有中间表/关联实体？没有 → 阻断。
- 弱实体（如用户券）是否有依赖标注？没有 → 建议。
- 是否有循环依赖（A→B→C→A）？有 → 阻断。

**ER 图与 PRD 一致性：**
- ER 图中的实体是否与 PRD 数据实体表一一对应？不一致 → 阻断。
- ER 图中的关系是否与 PRD 业务规则一致？不一致 → 阻断。
- ER 图中的外键是否与 DFD 数据存储一致？不一致 → 重要。
- ER 图中的属性类型是否与 API 契约一致？不一致 → 重要。

### 需要标记的反模式

| 反模式 | ER 图中的例子 | 为什么是问题 | 严重程度 |
|--------|-------------|-------------|---------|
| 无 ER 图 | PRD 只有数据实体表，没有 ER 图 | 开发无法直观理解关系 | 重要 |
| 实体遗漏 | PRD 有 4 个实体，ER 图只画了 3 个 | 遗漏实体关系未定义 | 阻断 |
| 关系缺失 | 用户和用户券之间没有画关系线 | 开发不知道 1:N 还是 N:M | 阻断 |
| 无 cardinality | 画了线但没标 1:N | 开发不知道是否需要中间表 | 重要 |
| N:M 无中间表 | 用户和优惠券画成 N:M 但没有关联实体 | 关系型数据库无法直接实现 | 阻断 |
| 属性冗余 | 用户实体和订单实体都有"手机号" | 更新不同步导致数据不一致 | 重要 |
| 关系与规则冲突 | PRD 写"一个用户可持有多张券"，ER 图画成 1:1 | 直接矛盾 | 阻断 |
| 循环依赖 | A 依赖 B，B 依赖 C，C 依赖 A | 数据库设计无法落地 | 阻断 |
| 主键设计不当 | 用业务字段（如手机号）做主键 | 业务字段可能变更 | 重要 |

## 评分指南

审查完 17 个维度后，给每个维度打分：

| 分数 | 含义 | 标准 |
|------|------|------|
| **3** | 优秀 | 无问题。所有必需元素齐全、具体、可测。 |
| **2** | 合格 | 仅有建议级问题。核心元素齐全但部分不够具体。 |
| **1** | 需改进 | 发现有重要问题。多个元素缺失或模糊。 |
| **0** | 严重缺失 | 有阻断级问题。核心章节完全缺失或矛盾。 |

### 结论判定规则

- **任意维度得 0 分** → 结论：🔴 阻断
- **任意维度得 1 分（且无 0 分）** → 结论：⚠️ 需修改
- **所有维度 ≥ 2 分** → 结论：✅ 可开发（有少量跟进项）
