# PRD 重生成指南

交互式问答完成后，进入 **PRD 重生成阶段**。本指南说明如何将原始 PRD + 审查报告 + PM 回答记录三者融合，生成一份开发可直接使用的完整 PRD，并按需生成配套验证图。

---

## 重生成的目标

```
原始 PRD（可能有缺失）+ PM 回答（补充了决策）→ 完整 PRD（开发可直接使用）
```

重生成的 PRD 不是在原文上打补丁，而是**重新组织**一份结构完整的文档，确保：

1. **每个功能模块都满足 11 项完整性标准**（见 `functional-module-framework.md`）
2. **每个审查问题都有对应的 PM 决策**，并体现在 PRD 中
3. **配套验证图按需生成**——PRD 里有内容支撑的图（状态机、流程、时序、ER、DFD、UX）由本阶段生成并嵌入；仍需人工产出的产物（如高保真原型）列入清单
4. **歧义消除**——所有模糊表述都已明确化
5. **可测可验**——验收标准具体、边界场景完整

---

## 重生成输入

| 输入 | 来源 | 用途 |
|------|------|------|
| 原始 PRD | 用户提供 | 保留原始意图和业务背景 |
| 审查报告 | 审查阶段产出 | 问题清单，对照确保每个问题都已解决；含阶段 1 模型推导记录，作为生成验证图的素材 |
| PM 回答记录 | 问答阶段产出 | 产品决策，直接写入 PRD 对应章节 |
| 功能模块框架 | `functional-module-framework.md` | 11 项完整性标准，作为结构模板 |

## 九、配套验证图与产物清单

### 9.1 配套验证图（本阶段按需生成）

按需生成——不是全量，PRD 里有什么才生成什么：

| 验证图 | 生成条件 | 状态 |
|--------|---------|------|
| 状态机图 | PRD 存在有状态实体 | ✅ 已生成 / ➖ 不适用 |
| 业务流程图 | PRD 存在核心业务流程 | ✅ 已生成 / ➖ 不适用 |
| 时序图（Sequence Diagram） | PRD 存在前后端交互场景 | ✅ 已生成 / ➖ 不适用 |
| ER 实体关系图 | 数据实体 ≥ 2 且有关联 | ✅ 已生成 / ➖ 不适用 |
| DFD 数据流图 | 数据流转跨多个模块/外部系统 | ✅ 已生成 / ➖ 不适用 |
| UX 用户流程图 | 用户路径对体验关键 | ✅ 已生成 / ➖ 不适用 |

生成与自检规则：

- **来源可追溯。** 图中每个状态、每条分支、每条线都必须可追溯到 PRD 原文、PM 阶段 2 确认的答案、或明确标注 ❓ 的行业默认值；禁止生成没有依据的分支、状态或关系。
- **逐图自检。** 每张图生成后按对应 framework 文件的标准自检（状态机无死锁/不可达状态、流程图分支穷尽、时序图先校验后提交、ER cardinality 完整、DFD 无黑洞白洞等）。自检发现图与 PRD 文字矛盾 → 以 PM 确认的答案为准修正 PRD 文字，并在修订标记中说明。
- **格式优先 Mermaid。** 图的用途是让 PM 可视化验证"PRD 说的是不是这个意思"，不是 PM 的交付物。

## 重生成规则

### 规则 1：保留原始意图

- 原始 PRD 中的业务背景、功能描述**保留原文**，不做改写
- 只在缺失处**补充**内容，不删除已有内容
- 如 PM 回答与原始 PRD 冲突，以 PM 回答为准并标注修订

### 规则 2：标注修订来源

每个修订处用以下标记说明来源：

| 标记 | 含义 | 格式 |
|------|------|------|
| 🆕 | 原始 PRD 中完全没有的新增内容 | `> 🆕 新增：[内容]（来源：PM 回答 Q5）` |
| 📝 | 基于原始内容修改的内容 | `> 📝 修订：[原内容] → [新内容]（来源：PM 回答 Q8）` |
| ❓ | PM 回答不明确，需再次确认 | `> ❓ 待确认：[问题]（PM 选择了"其他"但描述不够具体）` |

### 规则 3：完整性兜底

对于 PM 在问答中**未明确回答**的部分（如选了"其他"但描述模糊），按以下策略兜底：

| 情况 | 兜底策略 |
|------|---------|
| 异常场景未明确 | 填入行业默认方案 + 标注 ❓ 待确认 |
| 数据实体字段不完整 | 填入技术团队推荐字段 + 标注 📝 |
| 业务规则有歧义 | 列出所有可能解读 + 标注 ❓ 待确认 |
| 非功能性需求无指标 | 填入行业标准值 + 标注 📝 |

### 规则 4：配套验证图与产物标注

- 验证图按需生成、嵌入 PRD，每张图标注内容来源（PM 确认的答案编号 / PRD 原文 / ❓ 行业默认值）
- 每张图生成后按对应 framework 文件的标准自检
- 仍需人工产出的产物（如高保真原型、API 契约）列出负责人和预计完成时间

### 规则 5：验收标准自动推导

根据 PM 回答的业务规则和异常处理，自动生成验收用例：
- 每条业务规则 → 1 条正向验收 + 1 条反向验收
- 每个异常场景 → 1 条边界验收
- 所有非功能性需求 → 对应的验收指标

## 重生成质量检查

PRD 重生成完成后，进行自检：

| 检查项 | 标准 | 通过？ |
|--------|------|--------|
| 11 项功能模块完整性 | 每个模块都有必需章节 | ☐ |
| 审查问题全解决 | 每个阻断/重要问题都有对应 PM 回答和 PRD 修订 | ☐ |
| 歧义消除 | 不存在"等"、"相关"、"适当"等模糊词 | ☐ |
| 验收可测 | 每条验收标准都有具体预期结果 | ☐ |
| 异常覆盖 | 8 个必需异常场景全部覆盖 | ☐ |
| 数据实体完整 | 所有功能引用的实体都列出了属性 | ☐ |
| 业务规则有后果 | 每条规则都有"如果不遵守会怎样" | ☐ |
| 验证图可追溯且自检通过 | 按需生成的验证图每个状态/分支/关系都能指回 PRD 原文或 PM 答案，且通过对应 framework 自检；仍需人工产出的产物列出负责人 | ☐ |
| 修订标记完整 | 每处修订都标注了来源 | ☐ |
| ❓ 待确认项列出 | 所有 PM 回答不明确处都标注了 | ☐ |

## 输出格式

重生成的 PRD 通过 `html-report` skill 输出为 HTML 格式（无该 skill 时直接生成 HTML 文件或 Markdown，图用 Mermaid），包含：
1. 完整的 PRD 正文
2. 修订标记高亮显示（🆕 绿色 / 📝 黄色 / ❓ 红色）
3. 配套验证图（Mermaid 渲染，每张图标注内容来源）
4. 审查问题对照表（可折叠）
5. 交互式目录导航
