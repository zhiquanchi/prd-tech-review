# PRD 重生成与验证图生成

## 做什么

接收 `prd-review` 的交接物，执行审查闭环的最后一阶段：

```
原始 PRD（保留意图）+ 审查报告（问题清单）+ PM 回答记录（决策）
        ↓ 融合
完整 PRD（11 项模块完整性 + 🆕/📝/❓ 修订标记 + 可测验收）
        ↓ 按需
验证图 1–2 张（状态机/主流程/ER 等，Mermaid）+ 产物清单
```

**核心分工：PM 已做决策，AI 负责成稿与画图。** 重生成是**重新组织**一份结构完整的文档，不是原文打补丁。

## 输入契约（强制）

| 输入 | 必需？ | 说明 |
|------|--------|------|
| 原始 PRD | **必需** | 保留原始意图和业务背景 |
| 审查报告 | **必需** | prd-review 阶段 1 产出（问题表、维度分、模型推导记录）；缺失则先跑 prd-review |
| PM 回答记录 | 完整模式必需；轻量模式缺省 | 结构化决策（prd-review 阶段 2 产出）；轻量模式无回答 → 行业默认 + ❓ 兜底 |

## 加载预算（强制，控制上下文）

| 阶段 | 必读 | 条件读 |
|------|------|--------|
| 全流程 | `references/prd-regeneration-guide.md`（结构、修订、图、自检）；`references/functional-module-framework.md`（11 项结构模板） | 生成某类图 → 用 regeneration-guide §9.1 自检要点；prd-review 已安装时可参考其对应 `*-framework.md` 的自检段 |

## 工作流

1. 融合：原始 PRD + 审查报告 + PM 回答记录 → 完整 PRD（按 `functional-module-framework.md` 11 项组织模块章节）。
2. 修订标记：🆕 新增 / 📝 修订 / ❓ 待确认；未明确处行业默认 + ❓。每个修订处标注来源（PM 回答编号 / 审查问题号）。
3. 验收标准：业务规则 → 正反向用例；异常 → 边界用例；原始 PRD 无验收章节 → 代写标 🆕。
4. **按需**生成验证图：默认优先与本次决策相关的 **1–2 张**（通常状态机/主流程或 ER）；其余有把握的可一并生成，过多则写入产物清单标「可按需补生成」。每条边可追溯到原文、PM 答案或 ❓ 默认。
5. 图自检：按 regeneration-guide §9.1 要点；图文矛盾以 PM 确认为准改文字并标注修订。
6. 版本号：`V{主版本号}.tech-review.{YYYYMMDD}`，勿写死 V2.0。
7. 输出：完整 PRD + 图 + 产物清单 + 审查问题对照表（html-report 可选，否则 MD/HTML + Mermaid）。

用户明确要求「全量图 / 六图都要」时再生成全部适用类型。

## 修订标记（强制）

| 标记 | 含义 | 格式 |
|------|------|------|
| 🆕 | 原始 PRD 完全没有的新增内容 | `> 🆕 新增：[内容]（来源：PM 回答 Q5）` |
| 📝 | 基于原始内容修改 | `> 📝 修订：[原内容] → [新内容]（来源：PM 回答 Q8）` |
| ❓ | 未确认，需再次确认 | `> ❓ 待确认：[问题]（PM 选了「其他」但描述不具体）` |

## 完整性兜底（PM 未明确回答的部分）

| 情况 | 兜底策略 |
|------|---------|
| 异常场景未明确 | 行业默认方案 + ❓ 待确认 |
| 数据实体字段不完整 | 技术团队推荐字段 + 📝 |
| 业务规则有歧义 | 列出所有解读 + ❓ |
| 非功能性需求无指标 | 行业标准值 + 📝 |
| 时序图接口名无 API 契约 | 语义化命名 + ❓ 待 API 契约 |
