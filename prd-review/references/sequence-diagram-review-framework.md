# 时序图审查标准

维度 D16 审查时使用的基准，双重用途：PM 提供了时序图（Sequence Diagram）→ 阶段 1 按本标准**严格**审查；未提供 → **不因缺图定级/扣分**——按下方「本图关注点」核对 PRD 文字/表格/规则表是否覆盖，阶段 3 生成时序图（存在前后端交互场景时）后按本标准自检。时序图展示用户、前端、后端之间的调用顺序、消息传递和时序依赖。开发靠这个理解用户操作触发的接口交互顺序、请求-响应模式和异常处理逻辑。

## 本图关注点（无图时按此核对；形态无关）

时序图要验证的核心是**交互链路完整、调用顺序有依据**。无图时核对 PRD 文字/表格/规则表是否说清：

- 核心交互场景（登录、表单提交、列表查询等）的调用顺序明确？
- 链路完整：用户操作 → 前端校验 → 请求 → 后端处理 → 返回 → 前端展示？
- 接口名/端点明确（而非"调用接口"）？
- 异常路径（校验失败、网络错误、服务端异常）与失败回退明确？
- 与 PRD 操作规则一致（先校验后提交等）？

上述关注点被文字/表格覆盖即视为等价于有图，**不因缺图扣分**；时序图专业规范（画法要求节）仅在审查实际提供的时序图或 AI 生成图自检时使用。

---

## 1. 时序图完整性

### 查什么

时序图是否覆盖了所有涉及用户-前端-后端交互的核心场景？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 每个涉及前后端交互的核心功能都有时序图 | 登录、提交表单、查询列表、数据增删改都有时序图 | 只有部分场景有时序图 → 重要 |
| 时序图有明确的参与者定义 | 三个参与者：用户、前端、后端 | 参与者未定义 → 重要 |
| 时序图标注了同步/异步调用 | 每个箭头标注 sync/async | 未标注 → 建议 |
| 时序图标注了接口名称和 HTTP 方法 | 每个调用箭头标注具体接口名（如 `POST /api/login`、`GET /api/list`） | 未标注接口名 → 重要 |
| 核心异常路径有时序图 | 参数校验失败、权限不足、网络错误、服务端异常的时序路径 | 只有正常流程 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 参与者不完整 | 只画了前端和后端，没画用户操作起点 | 不知道操作触发来源和用户反馈路径 | 阻断 |
| 无异常路径 | 只画了正常提交成功流程 | 校验失败怎么提示？网络错误怎么处理？ | 重要 |
| 无请求-响应对应关系 | 只画了前端发请求，没画后端返回和用户反馈 | 开发不知道返回什么数据、怎么展示给用户 | 重要 |
| 循环/条件未标注 | 分页加载的循环逻辑没画出来 | 开发不知道是否需要循环加载、何时停止 | 建议 |
| 接口名缺失 | 箭头只写"调用接口" | 开发不知道调什么端点 | 重要 |

## 2. 时序正确性

### 查什么

用户操作→前端→后端的调用顺序是否符合业务逻辑？是否存在时序上的矛盾？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 用户操作触发顺序正确 | 用户点击 → 前端响应 → 发请求 → 后端处理 → 返回 → 前端展示 → 用户感知 | 时序缺少用户操作或用户反馈环节 → 重要 |
| 校验在前，操作在后 | 前端先校验表单，再发请求；后端先校验权限，再执行业务 | 先写数据再校验 → 阻断 |
| 状态更新顺序正确 | 用户操作 → 后端更新成功 → 前端刷新展示 → 用户看到结果 | 前端先改展示再请求后端 → 阻断 |
| 回退路径完整 | 后端操作失败时，前端回滚到操作前状态并提示用户 | 只有成功路径，失败时前端状态错乱 → 重要 |
| 并发控制点标注 | 重复提交防抖、请求竞态处理在时序图中标注 | 未标注并发控制 → 重要 |
| 异步操作时序正确 | 异步请求返回后再更新 UI，loading 状态展示时机正确 | 异步回调时序错误 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 缺少用户操作起点 | 时序图从前端发请求开始，没画用户点击/输入 | 开发不明确触发条件和用户意图 | 重要 |
| 缺少用户反馈环节 | 后端返回后就结束了，没画前端展示和用户感知 | 不知道 UI 上怎么呈现结果 | 建议 |
| 先改前端展示再发请求 | 用户点击后前端先改数据再调接口 | 接口失败后前端展示错误数据 → 数据不一致 | 阻断 |
| 无失败回退时序 | 提交失败时前端没画回退逻辑和错误提示 | 用户以为成功了，实际没保存 | 重要 |
| 多个请求竞态 | 用户快速切换 tab，先后发两个请求，后发的先返回 | 页面展示旧数据 | 重要 |
| loading 状态遗漏 | 发请求前没开 loading，返回后没关 loading | 用户不知道是否在加载，重复点击 | 建议 |
| 无防抖/节流 | 用户快速点击按钮发了 N 个请求 | 后端压力大，可能重复提交数据 | 重要 |

## 3. 时序图与 PRD 一致性

### 查什么

时序图中的调用顺序是否与 PRD 的操作规则表、业务规则一致？

### 审查标准

| 检查项 | 合格 | 缺失 |
|--------|------|------|
| 时序图中的每个步骤对应 PRD 操作规则表中的操作 | PRD 写了"用户点击→前端校验→提交请求→后端校验→执行业务→返回结果→前端展示"，时序图一一对应 | 时序图步骤与 PRD 不一致 → 阻断 |
| 时序图中的接口对应 API 契约 | 时序图调 `POST /api/form/submit`，API 文档有该端点 | 时序图接口在 API 文档中找不到 → 重要 |
| 时序图中的状态转换与状态机图一致 | 状态机图有"草稿→已提交"，时序图有对应的用户操作触发事件 | 不一致 → 阻断 |
| 时序图中的数据流与 DFD 一致 | DFD 中的数据流在时序图中有对应的接口调用 | 不一致 → 重要 |

### 反模式

| 反模式 | 例子 | 为什么是问题 | 严重程度 |
|--------|------|-------------|---------|
| 时序与操作规则冲突 | PRD 写"先校验再提交"，时序图"先提交再校验" | 直接矛盾 | 阻断 |
| 状态转换缺失 | 状态机图有 5 个状态，时序图只涉及 2 个 | 遗漏状态转换场景 | 重要 |
| 接口名不一致 | 时序图调 `submitForm`，API 文档叫 `createForm` | 开发不知道按哪个命名 | 重要 |

## 4. 推荐的时序图场景

以下场景涉及完整的"用户操作 → 前端 → 后端 → 用户反馈"链路，PRD 中存在这些场景时，阶段 3 应为其生成时序图：

| 场景 | 为什么必须有时序图 |
|------|-------------------|
| 用户登录/注册 | 涉及用户输入 → 前端校验 → 请求 → 后端鉴权 → 返回 → 前端跳转，需明确用户操作全链路 |
| 表单提交 | 用户填写 → 前端校验 → 提交请求 → 后端校验 → 业务处理 → 返回结果 → 前端反馈用户 |
| 列表查询/分页 | 用户搜索/翻页 → 前端组装参数 → 请求 → 返回数据 → 前端渲染 → 用户查看 |
| 文件上传/下载 | 用户选择文件 → 前端上传 → 后端处理 → 返回进度/结果 → 前端展示 → 用户感知 |
| 数据编辑/删除 | 用户点击操作 → 确认弹窗 → 发送请求 → 后端处理 → 返回结果 → 列表刷新 → 用户感知 |
| 高并发操作 | 用户快速点击 → 防抖/节流 → 竞态处理 → 幂等校验 |

## 5. 时序图画法要求

| 要求 | 说明 |
|------|------|
| 使用标准 UML 时序图语法 | 参与者、生命线、消息箭头、激活条、alt/opt/loop 片段 |
| 三个参与者，各一条生命线 | 用户、前端、后端 |
| 标注接口名和 HTTP 方法 | `POST /api/form/submit` 而非"调用提交接口" |
| 标注同步/异步 | sync 用实线箭头 + 虚线返回，async 用开放箭头 |
| 包含请求和响应 | 每条请求箭头对应一条响应箭头（除非是 fire-and-forget） |
| 包含用户操作起点 | 从用户操作（点击、输入、选择）开始画起 |
| 包含用户反馈终点 | 最终回到前端展示和用户感知 |
| 包含异常分支 | 用 alt 片段标注正常路径和异常路径（如 400、401、500） |
| 包含 loading 状态 | 标注前端 loading 的开始和结束时机 |

## 审查结论判定

时序图审查完成后，结合以下规则给 D16 维度打分：

| 分数 | 含义 | 标准 |
|------|------|------|
| **3** | 优秀 | 核心交互都有时序图，参与者完整、调用顺序正确、异常路径与用户反馈完整，与 PRD 完全一致。 |
| **2** | 合格 | 仅有建议级问题。时序图基本完整，少量 loading/接口名标注不够精确。 |
| **1** | 需改进 | 发现有重要问题。缺少部分场景、无异常路径、无失败回退、或与 PRD 有不一致。 |
| **0** | 严重缺失 | 有阻断级问题。缺用户操作起点、先改前端展示再发请求、或与 PRD 操作规则直接矛盾。 |

> 未提供时序图时不按本表打分——阶段 1 按「本图关注点」核对文字/表格覆盖度打分（见 review-checklist D16 评分指南），本表仅作为阶段 3 生成时序图的自检标准。
